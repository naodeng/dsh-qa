# DeepSeek Harness `dsh-v0.1.7-rc.1` 对 dsh-qa `v0.5.3` 的影响评估

> 评估日期：2026-09-24
> 上游目标：`dsh-v0.1.7-rc.1`，提交 `46a7f68b0922371ce7144b668b90e377d8e799f4`
> 当前项目：`dsh-qa v0.5.3`，`master` / `813bc39`
> 证据边界：本记录覆盖上游 Release 变更、当前仓库静态契约和本地测试；不把 RC 宿主实测、`quality-control` 实宿主运行或正式发布写成已完成。

## 结论

结论是：**存在条件性集成影响，但目前没有发现 `qa` 主路径已经命中 RC 破坏性变更的静态证据。** 当前 `v0.5.3` 可以继续作为兼容性基线，但暂时不能宣称“已验证兼容 `dsh-v0.1.7-rc.1`”。

当前状态应记录为：

`STATIC_CONTRACT_REVIEWED / LOCAL_UNIT_PASS / LOCAL_E2E_PASS / RC_HOST_NOT_RUN / QUALITY_CONTROL_HOST_NOT_RUN / RELEASE_NOT_ASSESSED`

## 上游 RC 中与本项目有关的变更

官方 RC 说明列出了以下迁移或兼容性关注点：

| 上游变更 | 对 dsh-qa 的判断 | 状态 |
| --- | --- | --- |
| Agent 预设改由插件 bundle 声明和安装，旧目录预设迁移 | 当前 `qa` 已通过 `dsh.bundle.patch` 加载 `preset/qa/cordis.patch.yml`，并使用 `@deepseek-ai/dsh-agent-preset` | `STATIC_PASS` |
| PTC 包名统一为 `ptc-runtime`，工作流执行器统一为 `workflow-ptc` | `qa` 和 `quality-control` 均已使用 `@deepseek-ai/dsh-workflow-ptc`，未发现旧 `dsh-workflow-worker-thread` | `STATIC_PASS` |
| `agent/session-start` 改为异步串行 `agent/created` | dsh-qa 没有直接监听或调用这两个生命周期事件；仅作为未来自动创建/编排能力的关注项 | `NO_DIRECT_HIT` |
| 弃用 `snapshotEvents`、`eventAt`、`ownEvents` | 当前 follow 读取 `snapshot.records` / `cursor`，单元测试明确禁止旧 API 名称 | `STATIC_PASS` |
| Remote 支持二进制结果，工作区读取统一为 `readBytes` | 当前代码只消费本项目使用的 JSON unary RPC 和 JSON follow snapshot；没有 Harness workspace `readBytes` 调用 | `CONDITIONAL` |
| 自定义事件中的附件不再自动读取或导出 | 当前仓库没有自定义事件附件读取/导出实现 | `NO_DIRECT_HIT` |
| Session 多实例、Session 日志 V4、插件兼容性检查 | 可能影响真实宿主的 Session 生命周期和安装/启动链路，但不能仅凭静态扫描确认 | `HOST_REQUIRED` |
| 官方 DeepSeek 适配器只使用 Messages API，旧 Chat Completions 配置需迁移 | 历史评估时 dsh-qa 主路径使用 DSH 原生 Session，未使用的 `server/deepseek.js` Chat Completions 实现仍在仓库中；当前已确认无调用者并删除该遗留模块 | `STATIC_CLEANUP` |
| Experimental Team 模式调整 `subagent` / `subagent_fork` | `quality-control` bundle 明确挂载了这两个 subagent 工具和 Ralph；当前只完成静态契约检查，未完成 RC 宿主运行 | `HOST_REQUIRED` |

上游原始说明见：[官方 `dsh-v0.1.7-rc.1` Release](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-rc.1)。

## 当前 dsh-qa 的实际命中面

当前 Workbench 浏览器侧使用的宿主契约仍是：

- `agentPresets/list`、`agentPresets/select`；
- `session/list`、`session/create`、`session/rename`、`session/modelCatalog`、`session/selectModel`、`session/prompt`、`session/cancel`；
- `skills/list`、`commands/list`、`commands/execute`；
- 通过 `/api/remote.mux` 建立 `session/follow`，解析 `snapshot.records` 和 `cursor`。

这些调用集中在 [`public/app.js`](../../public/app.js)、[`public/dsh-rpc-contract.js`](../../public/dsh-rpc-contract.js) 和 [`test/unit/dsh-compatibility.test.js`](../../test/unit/dsh-compatibility.test.js)。当前 bundle 元数据在 [`package.json`](../../package.json) 和 [`preset/qa/cordis.patch.yml`](../../preset/qa/cordis.patch.yml) 中已经是 0.1.7 时代的声明式安装形态。

需要特别注意：历史评估记录中的旧 Chat Completions 模块当时没有被当前 README、浏览器主路径或任何路由调用；后续静态检查确认它没有入口或包导出，现已删除。若未来重新引入独立模型调用路径，仍需按当时的 Messages API 迁移要求单独设计和验证。

## 验证结果

| 验证项 | 结果 | 说明 |
| --- | --- | --- |
| 官方 Release 与 RC commit | `VERIFIED` | Release 页面显示 `dsh-v0.1.7-rc.1` / `46a7f68` |
| 当前仓库版本与工作区 | `VERIFIED` | `master`、`v0.5.3`、工作区修改仅为本评估记录 |
| Unit/API | `PASS` | 162 passed |
| 独立模式 Chromium E2E | `PASS` | `QA_E2E_PORT=8913 npm run test:e2e`，32 passed |
| RC Host Smoke | `NOT_RUN` | 当前 [`test/playwright.host.config.js`](../../test/playwright.host.config.js) 只允许 `dsh-v0.1.7-alpha.1`，在未调整目标白名单前会直接拒绝 RC 版本；本轮没有把 alpha 结果冒充 RC 结果 |
| `quality-control` RC 实宿主运行 | `NOT_RUN` | 当前 Host Smoke 套件只覆盖默认 `qa` bundle，未覆盖独立 `quality-control` 安装、Session 创建和 subagent/Team 行为 |
| GitHub Release / npm 发布 | `NOT_ASSESSED` | 本次只评估上游 RC 对当前项目的影响，没有执行本项目发布动作 |

首次运行默认 `npm test` 时，单元测试已通过，但 E2E 因本机 `127.0.0.1:8899` 已被占用而未启动；随后使用仓库已有的端口覆盖运行，并在允许 Chromium 所需本机进程权限后完成 32 条 E2E。该端口冲突不属于 RC 兼容性失败。

## 结论后的最小动作

在正式记录 RC 兼容前，还需要：

1. 将 Host Smoke 的目标版本白名单和对应断言改为允许 `dsh-v0.1.7-rc.1`，保留精确版本检查。
2. 使用带认证的 RC 宿主 URL 重跑默认 `qa` Host Smoke，覆盖 Panel、Workbench iframe、preset、Session/RPC、follow、prompt 和刷新恢复。
3. 单独安装并运行 `quality-control` bundle，验证 `workflow-ptc`、`subagent` / `subagent_fork`、Ralph 和 Session 初始化。
4. 若上述宿主验证通过，再分别记录 GitHub Release、npm registry 和安装后启动结果；在此之前保持 `RELEASE_NOT_ASSESSED`。
