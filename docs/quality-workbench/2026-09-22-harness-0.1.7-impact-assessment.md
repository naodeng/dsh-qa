# DeepSeek Harness `dsh-v0.1.7-alpha.1` 对 dsh-qa `v0.5.0` 的版本影响评估与优化记录

> 评估日期：2026-09-22
> 评估范围：先只读检查上游官方 Release、上游 `dsh-v0.1.7-alpha.1` 源码与当前 dsh-qa 仓库文件，随后按结论完成本地 bundle/安装链路优化。
> 本文区分本地测试、静态检查与真实 Harness 0.1.7 宿主证据；真实宿主结果单独记录，不从局部通过推导完整兼容。

## 结论摘要

初始评估结论为：**有集成影响；当前 `dsh-qa v0.5.0` 不能直接宣称兼容 `dsh-v0.1.7-alpha.1`，但没有证据表明 0.1.7 必然破坏 0.5.0 的 Panel/Slot 或核心会话 RPC。** 本轮已修复静态 preset 安装契约冲突和两处 Host Smoke 暴露的问题，并由用户在真实 `0.1.7-alpha.1-c36a83f` 宿主完成最终 `6 passed`。因此，针对当前 `qa` bundle 覆盖的插件入口、Panel/Slot、Workbench、Session/RPC 和刷新恢复路径，可以记录为通过；`quality-control` 独立 bundle 的真实宿主运行和正式发布仍未评估。

已经确认并已处理的静态风险是 preset 安装契约发生了变化：0.1.7 的 Agent preset 注册表不再扫描目录，也不接受 preset 路径；preset 应通过插件组合包的 `@deepseek-ai/dsh-agent-preset` 配置行声明并安装到 profile。本轮将 `qa` 声明加入主插件 bundle，将 `quality-control` 改为独立 bundle，并把两个安装脚本改为调用 `dsh plugin --profile ... add link:...`。

其余影响目前应保持为条件性风险或未验证项：

- 当前工作台通过 JSON unary RPC、`/api/remote.mux` WebSocket 和 JSON session snapshot 工作；上游 0.1.7 新增的 unary 二进制结果主要影响会消费二进制结果的客户端，当前命中的会话、技能、命令和模型目录路径没有静态证据表明会返回二进制。
- 上游官方 DeepSeek 适配器改为只使用 Messages API，当前 dsh-qa 不直接调用模型供应商 API，只调用 Harness 的 `session/prompt` 和会话管理 RPC，因此没有直接命中点。
- 首次 0.1.7 真实宿主 Smoke 已证明插件入口、QA preset、Session create/rename、follow、model catalog、Skills、Commands、prompt、refresh/reconnect 路径通过；随后修复 popout 句柄和测试 frame readiness 时序，最终真实 Host Smoke 为 `6 passed`。

优化后兼容性状态应记录为：`STATIC_CONTRACT_REPAIRED / HOST_SMOKE_PASS / RELEASE_NOT_ASSESSED`。这表示目标 `qa` bundle 的真实 `dsh-v0.1.7-alpha.1` Host Smoke 已通过，不等同于 `quality-control` 独立 bundle 已完成真实宿主验证，也不等同于已经完成发布。

### 优化后已验证项

- `package.json` 的 `dsh.bundle.patch` 同时加载主插件 patch 与 `preset/qa/cordis.patch.yml`。
- `qa` 与 `quality-control` 均使用 `@deepseek-ai/dsh-agent-preset` 声明；`quality-control` 使用 `prefix` 和 `workflow-ptc`。
- 两个安装脚本均使用 profile bundle 安装，不再复制旧目录；支持 `--profile`、`--dsh` 和 `--dry-run`。
- Host Smoke 配置已锁定目标 `dsh-v0.1.7-alpha.1`；前两次真实结果均为 `5 passed / 1 failed`，分别暴露了 `window.open(..., 'noopener')` 空句柄和 iframe frame readiness 时序问题，已分别在 [`lib/client.js`](../../lib/client.js)、[`client-runtime.test.js`](../../test/unit/client-runtime.test.js) 与 [`dsh-panel-lifecycle.spec.js`](../../test/e2e/dsh-panel-lifecycle.spec.js) 修复；最终真实 Host Smoke 为 `6 passed`。

## 2. 优化前 dsh-qa `v0.5.0` 命中点

### 2.1 优化前已确认的高风险命中：preset 安装和发现

优化前仓库的证据链是：

1. `package.json` 版本为 `0.5.0`，并通过 `dsh.bundle.patch` 只声明 dsh-qa 自身的 `cordis.patch.yml`：[`package.json`](../../package.json#L2-L22)。
2. `cordis.patch.yml` 插入的只有 `id: dsh-qa` 的插件行，没有 `@deepseek-ai/dsh-agent-preset` preset 声明：[`cordis.patch.yml`](../../cordis.patch.yml#L1-L8)。
3. 评估前的 `install-qa-preset.sh` 把 `agent.cordis.yml`、`preset.yml` 复制到旧目录；本轮已改为 profile bundle 安装：[`install-qa-preset.sh`](../../scripts/install-qa-preset.sh)。
4. 评估前的 `install-quality-control-preset.sh` 同样写入旧目录；本轮已改为安装独立 bundle：[`install-quality-control-preset.sh`](../../scripts/install-quality-control-preset.sh)。
5. 工作台首次进入项目时调用 `agentPresets/list`，查找 `id=qa`；找不到时直接抛出“未找到测试模式 preset”，不会继续创建/绑定 session：[`public/app.js`](../../public/app.js#L636-L645)。

这与上游 0.1.7 preset 注册表“不扫描目录”的官方契约形成直接冲突。因此可以确认：**优化前安装脚本和 0.1.7 的新 preset 发现模型不兼容。** 本轮已将主 `qa` 与可选 `quality-control` 都迁移为 bundle 声明；这仍是静态修复结论，不等同于已经在 0.1.7 宿主运行并观察到成功。

### 2.2 另一个 preset 命中：`quality-control` 的 persona 字段

优化前的 `quality-control` preset 使用 `@deepseek-ai/dsh-persona` 的 `config.text`；本轮已移除旧目录组合，当前独立 bundle 使用 `prefix`：[`cordis.patch.yml`](../../preset/quality-control/cordis.patch.yml)。上游 0.1.7 的 `dsh-persona` 配置要求 `prefix` 为必填字段，且其官方示例和 schema 以 `prefix` 为人设文本字段：[上游 persona 文档](https://github.com/deepseek-ai/deepseek-harness/blob/c36a83ff6bb95e3f82cf79f9be7c724270a8aa61/packages/preset/persona/README.zh.md#%E9%85%8D%E7%BD%AE)。

因此 `quality-control` 的原配置在 0.1.7 上存在配置校验风险；本轮新增了独立 bundle 和静态契约测试，但仍没有新宿主挂载证据。这一项应标为 `STATIC_CONTRACT_REPAIRED / HOST_NOT_RUN`，而不是已确认的运行时成功。

### 2.3 Panel/Slot：当前代码与上游 0.1.7 契约仍对齐，但未重新验收

当前 `lib/client.js` 使用：

- `sidebar.panellist` 注册入口；
- root `main` keyed slot，以 `dsh-qa` 作为 key；
- `ctx.layout.selectPanel(null)` 返回会话面板；
- 由 Harness 提供 React runtime，保留 iframe 和 disposer。

证据见 [`lib/client.js`](../../lib/client.js#L1-L60)。上游 0.1.7 仍在官方 [UI Sidebar 文档](https://github.com/deepseek-ai/deepseek-harness/blob/c36a83ff6bb95e3f82cf79f9be7c724270a8aa61/packages/client/ui-sidebar/README.zh.md#%E6%8F%92%E4%BB%B6%E6%B7%BB%E5%8A%A0%E9%9D%A2%E6%9D%BF%E5%9B%BE%E6%A0%87)描述 `sidebar.panellist` 与相同 id 的 `main` keyed slot，也在 [UI Layout 文档](https://github.com/deepseek-ai/deepseek-harness/blob/c36a83ff6bb95e3f82cf79f9be7c724270a8aa61/packages/client/ui-layout/README.zh.md#%E5%85%A8%E5%B1%80%E9%9D%A2%E6%9D%BF)保留 `selectPanel()`。

因此静态结论是 `NO_DIRECT_BREAK_EVIDENCE`；但当前仓库的真实宿主证据仍锁定 `dsh-v0.1.6-alpha.1`，记录在 [`2026-09-15-harness-compatibility.md`](./2026-09-15-harness-compatibility.md#1-目标版本)。不能把 0.1.6 的 `5 passed / 1 skipped` 结果折算为 0.1.7 兼容证明。

### 2.4 Session/RPC/Remote：命中旧边界，但未发现直接删除

当前工作台的 RPC 与 follow 证据如下：

- unary 请求统一发送 `client-request`，响应按 JSON 读取：[`public/dsh-rpc-contract.js`](../../public/dsh-rpc-contract.js#L1-L40)；
- follow 通过 `/api/remote.mux` 建立 WebSocket：[`public/app.js`](../../public/app.js#L111-L119)；
- follow open envelope 使用 `session/follow`、`request.address`、`maxMessages`，并读取 `snapshot.records`/`cursor`：[`public/dsh-rpc-contract.js`](../../public/dsh-rpc-contract.js#L42-L64)；
- 工作台调用 `agentPresets/list`、`session/*`、`skills/list`、`commands/list`，普通 prompt 通过 `session/prompt` 提交：[`public/app.js`](../../public/app.js#L636-L705)、[`public/app.js`](../../public/app.js#L816-L865)。

上游 0.1.7 仍保留 `/api/remote.mux`，并明确没有附件的 unary 结果继续使用 JSON；上游 Remote 文档也把浏览器流项描述为 JSON 安全值。因此当前路径没有静态的直接删除或改名证据。另一方面，当前 `createDshRpc()` 对所有 unary 结果直接调用 `response.json()`，`openFollowSnapshot()` 对所有 WebSocket message 直接 `JSON.parse(event.data)`；如果未来 dsh-qa 接入会返回二进制结果的 endpoint，现有解析器不能直接承载该协议。当前调用清单没有发现这类 endpoint，仍需新宿主验证。

状态：`NO_DIRECT_BREAK_EVIDENCE / CONDITIONAL_BINARY_RISK / HOST_NOT_RUN`。

### 2.5 Messages API、`readBytes`、附件：当前仓库没有直接调用点

当前仓库的直接检索结果没有发现 `readBytes`、Harness workspace `readFile`、DeepSeek provider HTTP、Chat Completions、附件上传/导出或自定义事件附件消费代码。dsh-qa 自己的产品数据由 Node HTTP/SSE/JSON store 管理；模型调用和文件工具由 Harness session/preset 提供。

因此：

- Messages API 变更是对 Harness provider 层的间接影响，不是 dsh-qa 当前源码直接调用的 API。
- `readBytes` 迁移要求暂未命中 dsh-qa 自有代码；若未来将 0.6.0 Host Execution 接入 Harness workspace/file Remote，需要重新评估。
- 附件自定义事件变化暂未命中当前 0.5.0 主路径。

## 3. 仍未完成的验证和证据边界

下列事项本次仍未完成，不能用局部通过结果替代：

1. 在 0.1.7 中单独验证当前安装脚本与旧目录迁移路径的行为；Host Smoke 证明了新 `qa` bundle 被发现，不覆盖所有安装迁移场景。
2. 验证 `quality-control` preset 的新 bundle 声明、`prefix` 字段及其完整插件组合能否在真实宿主启动。
3. 验证 0.1.7 的二进制 unary 响应是否会出现在当前 dsh-qa 已调用的 endpoint；当前源码/文档分析只能说明协议存在，不能证明具体 endpoint 永不返回二进制。

当前仓库已有的宿主证据包括历史 `dsh-v0.1.6-alpha.1` 和用户提供的 `dsh-v0.1.7-alpha.1-c36a83f` 最终 `6 passed` 结果；后者覆盖 `qa` bundle 的目标 Host Smoke，不覆盖 `quality-control` 运行验证或发布状态。
