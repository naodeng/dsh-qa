## 二、仍然是 P0 的 7 个问题

### 1. 首页 DSH 对话没有固定在视口内，输入框在首屏之外

这是最直接、最影响使用的问题。桌面 1440×900 下实测：

```
copilot-input top = 1075px
viewport height = 900px
page height = 1121px
```

也就是说，**打开首页时看不到聊天输入框**，必须向下滚动整页才能发消息。右侧对话栏的消息区不会独立滚动，输入框跟着页面底部走。当前版本是固定 chat pane，输入框始终在视口内；v2 退化了。

需要：

- 右侧 Copilot 栏设为 `sticky` 或 `h-[calc(100vh-顶栏高度)]`；
- 消息区独立 `overflow-y-auto`；
- 输入区固定在栏底；
- 首页主内容独立滚动，不要把整页高度撑到对话栏下方。

移动端同理：首页的「DSH 对话」按钮只是 `scrollIntoView`，没有打开 `dsh_1` 的全屏 sheet；应该直接打开全屏 sheet，而不是滚到页面底部。

### 2. 日历「月视图」不是一个月

`_2` 的月视图在 1440 下只有 9 个日期格（23–29 + 12-03），不是 42 格月历；在 390 下变成 2 列共 9 格，更接近列表。这不是「月视图」，也不是当前版本的完整月历。

同时缺：

- 年份/月份下拉；
- 日期跳转输入；
- 选中日期的删除；
- 「接下来 30 天」；
- 移动端真正的议程模式（当前是 2 列日期列表，但标题仍叫“月视图”）；
- 周视图只有 4 天，不是完整 7 天。

当前版本 `renderFullCalendar()` 有完整 42 格、年/月选择、日期跳转、删除、接下来 30 天。v2 不能把这些删掉。

### 3. 移动端看板不完整，卡片不可进入

`dsh_1` 的移动看板只有 3 个阶段（用例设计 / 需求分析 / 已发布），缺用例评审、执行中、缺陷回归。更严重的是：**卡片没有「预览」「详情」按钮，也不是链接**，在移动端无法打开项目。

需要：

- 6 个阶段都有；
- 卡片可点击进入工作区，或有「预览/详情」；
- 保留逾期/风险、真实计数；
- 移动端阶段切换器带 `aria-selected`；
- 空阶段有明确提示。

### 4. 项目工作区深度仍然不够

v2 的工作区有了 6 个 tab，但每个 tab 的内容比现版本薄很多：

- **项目概况**：只有 4 个指标 + 基础信息。缺「建议下一步/行动队列」、需求覆盖概览、质量任务列表、近期动态、项目资料（成员/策略/工作区/阶段历史/编辑/删除）。
- **需求与用例**：矩阵缺验收标准、覆盖状态、风险、搜索/筛选、用例详情（前置/步骤/预期/风险）、用例状态编辑；多了没有数据支撑的「关联缺陷」列；「新建需求 / 新建用例 / 关联需求」不是现有 UI/API。
- **质量任务**：只有一张任务卡（验收/范围/风险/最近运行）。缺任务列表、来源、决策、测试计划、运行、证据、故障分析、回归集、执行配置、Host 配置、项目级运行/记录、新建任务/计算回归集/新建故障分析/确认缺陷。
- **缺陷与风险**：只有一条缺陷。缺状态筛选、环境/模块/频率/影响、复现/预期/实际、证据引用、详情展开、质量任务风险列表；「关联需求/关联用例」没有数据模型。
- **证据与交付**：缺「评估质量门禁」和任务选择器；checks 状态/结论自相矛盾（见第 6 点）；缺待审批门禁列表、报告版本、门禁趋势、证据包状态/下载/清理任务；「报告」和「测试运行」混用。
- **活动时间线**：只有里程碑、一份资料、一条纪要。缺待安排/已结束日程、新增日程、知识、阶段历史/材料动态。
- **上下文检查器**：只有标题、描述、两个通用按钮；没有按实体展示字段，也没有编辑/状态流转。

如果目标是「UI 跟随现有功能」，这块是最大的剩余工作量。

### 5. 新建项目 / 新建日程 / 设置表单缺字段，且新增了不存在的行为

**新建项目**：

- 缺 `projectKey`（项目编号）、`product`（被测产品）、`owner`（负责人）、`members`（成员）、`assistant`（辅助模式/自动提取/提醒）、`createWorkspace`。
- 「自动生成 PRJ-YYYY-NNN」不是现有行为：`projectKey` 是可选输入，`createProject()` 不会自动生成编号。照此实现会得到空编号。
- 「初始阶段」不是现有行为：`createProject()` 固定 `status: 'intake'`。
- 「所属域 (domain)」不是现有字段：现版本叫「被测产品」，对应 `product`。

**新建迭代**：

- 增加了「关联主项目」，`parentId` 字段存在，API 也接受，属于可做的 UI-only 改进；但当前 UI 没有这个入口，需要确认是否本期做。
- 「自动生成 ITER-YYYY-NNN」同样不存在。

**新建日程**：

- 缺「关联项目」（API 必须按项目创建）；
- 缺「日程 / 里程碑」切换；
- 缺 `kind`（会议/评审/发布/其他，里程碑另有 release/review/freeze/other）；
- 缺备注/依据；
- 当前表单只靠 title/date/type 无法写入现有数据模型。

**设置**：

- 缺 DSH 预设（qa / quality-control）、最新版本、更新提示、发布记录、仓库、官网；
- 只有 3 个面板，缺辅助策略、质量任务、执行配置、Host 配置、门禁例外、确认/输入、发布记录、技能与命令等现有弹窗；
- 没有真正的 modal chrome（关闭、Escape、焦点陷阱、焦点恢复）；
- 「清理示例数据」没有二次确认。

### 6. 门禁 checks 的状态/结论自相矛盾

这是最需要在实现前对齐的语义问题。设计里出现：

```
stale-evidence       → WARN
verified-evidence    → PASS
critical-test-result → PASS
critical-risk        → BLOCK
medium-coverage      → WARN
整体结论             → WARN
```

现有模型不是这样：

- 每项 check 的状态是 `passed / failed`，严重级别是 `block / warn`，不是 `PASS / WARN / BLOCK`；
- `stale-evidence` 是 `block` 级别，失败时整体就是 `BLOCK`，不会单独显示 WARN；
- `critical-risk` 失败是 `block`，整体也是 `BLOCK`，不可能同时存在「critical-risk BLOCK + 整体 WARN」；
- `medium-coverage` 是「中高风险覆盖度」，不是「需求用例覆盖度」；它是可豁免项；
- `stale-evidence` 不可豁免，设计里「可为 stale-evidence 或 medium-coverage 记录临时豁免」是错的；
- 人工审批是独立于 check 的 gate，不是「PASS 的必要条件」；现有发布流转只检查项目级门禁是否 blocked，不要求 approval approved；
- 看板「门禁阻断（BLOCK / WARN）」也不准确：WARN 不一定会阻断发布，只有项目级 blockers 才阻断；
- 「已发布」空列写「PASS + approved」是设计新加的规则，不是现有规则。

需要一张准确的表（见第五节）。

### 7. 仍然存在的假动作 / 假字段

虽然 v2 删了很多，但还有：

- 「+ 新建需求」「+ 新建用例」「关联需求」：当前没有对应 UI/API，只有 AI 工具 `requirement_add / testcase_add / testcase_link`；手动按钮是新增功能。
- 「关联缺陷」列、「缺陷关联需求/用例」：当前 requirement 只关联 testcase；defect 没有 requirementId/testcaseId 字段。
- 「执行测试」一键按钮：真实 Host 执行需要 profile + target + capability + timeout + preview + confirm；没有这种一键入口。
- 「策略：并发 2 · 超时 300s」：`concurrency` 不是现有字段；timeout 有，但并发没有。
- 「最近运行状态：WARN」「run_410e9a · DSH 测试模式」：测试运行状态是 queued/running/passed/failed/...，没有 WARN；DSH 测试模式是对话 preset，不是测试运行执行器。
- 「报告」tab 展示 `run_410e9a`：report 是文档（docType/versions），test run 是执行记录，两者不能混。
- 「数据保存在本地 SQLite」：实际是本地 JSON 文件（`data.json`）+ 项目目录，不是 SQLite。
- Skills 的 12 个示例技能里，10 个在真实目录中不存在（只有 `api-testing`、`test-strategy` 存在）；`已安装 3` 也是假状态。
- `/regression-testing`、`/bug-triage` 不是真实技能；`deepseek-chat` 是写死的模型，实际模型来自 DSH。
- 仪表盘行动队列写 5 条但只画 3 条；「打开行动台」只是过滤，不是行动台。
- 「快速预览」在首页链接到看板页，不是抽屉。
- 「设为对话上下文」只改 badge，没有选中态，也不加载对应项目会话。
- 「清理示例数据」只是隐藏 banner，没有确认/API。
- 版本号链接到设置页，没有发布记录弹窗。

## 五、门禁语义正确表（实现前必须对齐）

| 设计写法 | 现有模型 | 正确的 UI 表达 |
| --- | --- | --- |
| `stale-evidence = WARN` | check 状态 passed/failed，severity block | 显示 `failed` + `block`；整体 BLOCK |
| `critical-risk = BLOCK` + 整体 WARN | failed + severity block → 整体 BLOCK | 整体必须是 BLOCK |
| `medium-coverage = 需求用例覆盖度` | 中高风险覆盖度，severity warn，waivable | 改「中高风险覆盖」，可豁免 |
| `PASS` 要求 approval approved | gate PASS 只看 checks；approval 是独立 gate | PASS 与 approval 分开展示 |
| `WARN` 阻断发布 | 只有项目级 blockers 阻断 | 写「存在项目级阻断」而不是 WARN |
| 可为 `stale-evidence` 或 `medium-coverage` 豁免 | 只有 waivable 的 check 能豁免；stale-evidence 不可 | 只给可豁免项显示「新增豁免」 |
| 一个 `approval: pending` | 可能有多个人工审批 gate | 显示待审批 gate 列表，而不是单个 badge |
| 证据「清理」立即删除 | 创建 artifact cleanup job，需确认 | 确认 + 清理任务状态 |
| 「报告」与「运行」混用 | reports / testruns 两类 | 分开显示 |

建议在 UI 上直接展示五项 checks 的 `passed/failed`、severity、explanation、evidenceRefs、waived，再单独显示 verdict 和 approval gates。这样既准确，也能解释为什么 BLOCK。

## 六、全局导航与移动端

### 全局顶栏

当前 6 个页面顶栏并不统一：

- 首页/看板：搜索 + 连接 + 新建 + 设置。
- 日历/工作区/Skills：连接 + 新建 + 设置，**没有搜索**。
- 设置页：只有连接状态，**没有搜索/新建/设置**。

需要统一成一个组件，所有页面都有：全局搜索、新建项目/迭代、设置、版本/发布记录、返回 DSH、连接状态。否则「全局搜索」不成立。

另外：**没有全局 DSH 对话入口**。用户决定不单独做对话页，那么从看板/日历/Skills/工作区应该能一键打开首页对话（并带入当前项目上下文），而不是必须先回首页。

### 移动端

- 首页移动端只画了 2 个指标 + 1 条待办；缺行动队列、项目列表、日程、AI/动态。至少要让用户能滚动看到完整模块，或明确「移动端只做分诊」。
- 移动看板只有 3 阶段、卡片不可进入。
- 移动工作区的需求矩阵仍是表格，390px 下「关联缺陷」列被截断，要求标题换行 4–5 行；应改成堆叠卡片。
- 移动日历仍是 2 列日期列表，标题叫「月视图」；应改成议程模式，或真正 7 列。
- 移动顶栏的新建项目/迭代被 `hidden sm:` 隐藏，「更多」打开的是快速设置，不是新建菜单。
- 对话全屏 sheet 缺模型/新对话/技能浏览/附件 chips/恢复/雷达详情/策略/历史状态；输入区固定是好的。

## 七、暗色、英文、无障碍、交接

### 暗色

- dark tokens 已经补了，首页/工作区/看板的观感不错。
- 但页面 Tailwind config 的 `outline` 仍是 `#737686`，设计系统写的是 `#5D6170`；后者是为对比度修正的，页面没同步。12px 小字在 `#F7F7F5` 上仍会低于 AA。
- 页面里大量 `dark:bg-[#...]` 硬编码，没有用 tokens；实现时需要映射到 CSS variables，否则换主题/品牌会散。
- 需要补 dark 下的：日历、Skills、弹窗、状态、表格、Toast、空态、错误态截图。

### 英文

- 目前只有零散的 `data-i18n` 字典，页面大部分按钮/表头/状态/说明仍是硬编码中文；语言切换只翻译了标题和少量标签。
- 需要完整的英文文案表，并检查 390px 下英文膨胀（导航、按钮、状态徽标、表格列头）。
- 设计系统说 30–40% headroom，但实际布局没有为英文留空间（如顶栏、tab、卡片按钮）。

### 无障碍

- 6 个分区 tab、看板移动阶段、抽屉 tab 都用了 `role="tablist"`，但按钮没有 `role="tab"`、`aria-selected`、`aria-controls`。
- 抽屉/弹窗没有焦点陷阱、Escape、焦点恢复的说明；当前版本有。
- 关闭按钮、纯图标按钮需要可聚焦 `<button>` 和 `aria-label`。
- 移动端表格/卡片点击区域、12px 中文、状态只靠颜色（部分有文字，基本 OK）。
- 需要补 `:focus-visible`（已有）、`prefers-reduced-motion`（已有）、键盘操作/拖拽替代。

### 设计交接

- `dsh_qa_design_system.md` 仍引用 `components/` 下的组件文件，但目录里没有 `components/`；实现者只能从页面反推组件。
- 字体仍是 Google Fonts 的 Red Hat/Instrument Sans，中文会回退；本地/离线场景需要系统字体或本地 woff2。
- 仍使用 Tailwind CDN；项目是零生产依赖、无构建，落地需要手写 CSS 组件层或引入构建，二者要先定。
- 页面中重复的顶栏/卡片/状态组件没有抽成统一 spec，后续改动容易各页不一致。
