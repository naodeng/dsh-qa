# DSH QA Workbench 迭代需求文档

## 1. 项目决策

- 代码仓库、插件 ID、npm 包名继续使用 `dsh-qa`。
- 产品展示名升级为 DSH QA Workbench（研发质量控制工作台）。
- 不新建第二套前端、第二个仓库或第二套数据迁移路径。
- 当前迭代目标为 `0.2.0`：质量任务与风险分析。

## 2. 背景与问题

现有工作台已经覆盖项目、迭代、需求、用例、缺陷、里程碑、QA 看板和质量控制室，但需求风险、人工决策和测试范围之间缺少可追踪的质量任务。第一阶段先补上这条链路，避免一开始建设完整测试平台而扩大风险。

## 3. 用户与场景

### QA

从现有项目创建质量任务，绑定需求文件或 Git diff，查看风险并确认测试范围。

### 产品/项目负责人

查看高风险项，确认、接受或保留待处理状态，并了解当前质量阶段。

### 开发者

提交变更后获得变更风险和建议测试范围；未执行测试时不能误显示为通过。

## 4. `0.2.0` 范围

### 必须交付

- `QualityTask`：项目内可追踪的质量分析任务。
- `Risk`：包含严重度、来源、证据和处理状态的风险项。
- `QualityStage`：任务当前质量阶段。
- `HumanDecision`：对风险和建议的确认、接受或拒绝记录。
- 现有项目需求记录、项目工作区内需求文件与受控 Git diff 快照绑定。
- 风险分析结果、可追溯验收标准和建议测试范围。
- 项目详情页中的质量任务、验收标准、风险清单、质量阶段、待人工确认区域，以及 QA、开发、产品/项目三种只读展示视角。
- DSH 工具能力：`qa_quality_task_get`、`qa_quality_analysis_save`、`qa_quality_risk_decide`、`qa_quality_test_scope_suggest`。创建任务由工作台 API/UI 完成；DSH 工具读取任务、保存分析、追加风险决定和更新测试范围。

### 明确不做

- 本迭代不实现测试执行器、证据包、缺陷自动创建、回归计算或质量门禁。
- 不改变现有项目、看板、用例、缺陷的数据格式和路由契约。
- 不引入生产依赖或新的前端框架。

## 5. API 需求

```text
POST /api/projects/:projectId/quality-tasks
GET  /api/projects/:projectId/quality-tasks
GET  /api/projects/:projectId/quality-tasks/:id
POST /api/projects/:projectId/quality-tasks/:id/analysis-requests
POST /api/projects/:projectId/quality-tasks/:id/manual-analyses
POST /api/projects/:projectId/quality-tasks/:id/decisions
```

所有更新既有实体的写操作必须校验项目归属、必填字段、`expectedRevision` 和允许的状态迁移；创建操作不要求 revision。QualityTask 为兼容首版内部字段，可把现有 `version` 映射为公开 revision；TestPlan/Profile 的业务 `version` 不能替代并发 revision。错误响应沿用现有 API 结构。独立模式的手工分析必须明确提交 `origin=manual`、`actorLabel` 和当前来源摘要，不能伪造 DSH session 或 `origin=agent`。

## 6. 验收标准

1. 能从现有项目创建质量任务。
2. 任务能绑定需求文件或 Git diff，并保留来源信息。
3. 分析结果至少包含验收标准、风险清单、风险级别、分析依据和建议测试范围。
4. 风险可标记为待确认、已确认、已接受或已拒绝，并记录操作者与时间。
5. 质量阶段可被用户观察，且阶段变化有明确规则。
6. 没有测试执行证据时，界面和 API 都不能宣称 `PASS`。
7. 现有项目、看板、用例和缺陷流程回归通过。

## 7. 后续版本目标

- `0.3.0`：测试策略、测试用例和 Node/Playwright 测试执行。
- `0.4.0`：截图、trace、日志、Git commit 绑定、缺陷与回归分析。
- `0.5.0`：PASS/WARN/BLOCK 质量门禁、发布报告和人工风险接受。

## 8. 产品目标与度量

### 目标

将“需求理解、变更识别、风险判断、测试建议、人工决策”串成可追踪记录，使质量结论有来源、有责任人、有时间线，并为后续测试执行和质量门禁提供稳定输入。

### 非目标

本产品不替代项目管理系统、代码托管平台、CI 平台或人工发布审批；它聚合质量信息并辅助决策，不自动替用户承担发布责任。

### 建议度量

| 指标 | 定义 | `0.2.0` 要求 |
| --- | --- | --- |
| 任务可追溯率 | 有合法来源和分析记录的质量任务 / 全部质量任务 | 100% |
| 风险处理率 | 已确认/已接受/已拒绝风险 / 全部风险 | 页面可见，不设自动达标线 |
| 误通过率 | 无执行证据却显示 PASS 的任务数 | 0 |
| 决策完整率 | 有操作者、动作、理由、时间的决策 / 全部决策 | 100% |

## 9. 角色、权限与责任

| 角色 | 可执行动作 | 不可执行动作 |
| --- | --- | --- |
| QA | 创建任务、运行分析、确认风险、调整测试范围 | 代替发布负责人接受业务风险 |
| 产品/项目负责人 | 查看任务、确认或接受业务风险 | 修改分析原文和来源摘要 |
| 开发者 | 提供 diff、查看结果、补充技术说明 | 删除决策记录 |
| 系统/Agent | 生成候选风险和测试建议 | 自动确认风险、自动宣称通过 |

`0.2.0` 不引入登录和角色鉴权。独立本地模式下记录的是用户填写的 `actorLabel`，它是审计提示而非可信身份；通过 DSH 宿主调用时，同时记录宿主提供的 `dshSessionId`。文档和界面不得把 `actorLabel` 描述为已认证用户。真正的角色授权不在本路线范围内。

## 10. 用户流程与异常流程

### 正常流程

1. 用户进入项目详情，点击“新建质量任务”。
2. 填写标题、目标、来源类型和来源引用。
3. 系统校验项目归属和来源可读性，创建 `intake` 任务。
4. 在 DSH 模式中，用户从项目会话触发分析，DSH 调用质量工具回写结构化结果；独立模式通过专用 manual-analysis API 创建任务、手工录入和查看结果，结果始终显示“人工录入”。
5. 系统保存来源快照、分析版本、风险和测试范围，任务进入 `confirmation`。
6. 责任人逐项确认，任务在规则满足后进入 `ready`。

### 异常流程

- 来源不存在：任务保留在 `intake`，显示可修复错误，不生成空风险。
- 来源过大或格式不支持：返回明确错误码，保留用户输入但不写入分析结论。
- 分析失败：保留失败时间和错误摘要，任务停在 `analysis`，允许重试。
- 并发确认：服务端按最新版本校验，冲突返回 409，不覆盖已有决策。
- 浏览器刷新：从持久化任务恢复状态，不能把加载状态误显示为通过。

## 11. 版本完成定义

`0.2.0` 只有在以下条件全部满足时才可交付：API 契约、状态规则、项目边界、单元/API/E2E 测试和文档均完成；空状态、错误状态、刷新恢复、重复分析和高风险阻断均有验证；全量测试通过且无未解释的 `PASS`。

## 12. 各迭代详细需求

### 12.1 `0.2.0` 质量任务与风险分析

**用户价值：** 把需求或代码变更转成可确认的风险和测试范围。

**输入：** 项目、任务标题、现有需求 ID、项目工作区内 UTF-8 文本文件或项目工作区 Git 仓库生成的文本 diff、可选补充说明。`0.2.0` 不支持浏览器任意路径、二进制来源和材料上传。单个来源快照最多 1 MiB，单任务当前来源合计最多 5 MiB；超过限制必须拒绝，不能静默截断后继续分析。

**输出：** 验收标准、风险清单、风险严重度、证据引用、建议测试范围、人工决策和当前阶段。

**核心流程：** `创建任务 → 校验来源 → 分析 → 人工确认 → ready`。

**完成条件：** 至少存在一条验收标准和一项测试范围，且每条验收标准和风险都能回溯到来源；confirmed 且 disposition 仍为 open 的高风险不能 `ready`；失败分析可重试；不生成测试通过结论；角色视角只改变展示，不产生三份数据。

**不做：** 不执行测试，不自动创建缺陷，不生成发布门禁。

### 12.2 `0.3.0` 测试策略与测试执行

**用户价值：** 将 `0.2.0` 的建议测试范围变成可执行、可重复、可追踪的测试计划。

**输入：** `QualityTask`、风险、`testScope`、项目工作区和项目预先保存的执行配置。`0.3.0` 不接受浏览器提交任意命令。

**输出：** `TestPlan`、复用 `project.testcases` 创建或关联的 `TestCase`、`TestRun`、执行状态、退出码、日志摘要和失败原因。

**核心流程：** `风险/范围 → 测试计划草稿 → 用例审查 → 人工确认计划版本 → 选择执行器 → 执行 → 结果归档`。

**必须支持：** Node 内置测试、Playwright 测试；运行中、通过、失败、取消、超时和环境错误；重复运行保留历史；执行前显示服务端解析后的工作目录、命令参数、artifact 写入范围、外部网络策略和需要确认的影响。用户确认必须绑定该预览摘要，配置变化后旧确认失效。

**安全要求：** 只允许预定义执行器、精确测试文件和命令模板；禁止任意 shell 拼接、glob 展开、`npx` 自动下载；限制工作目录为项目范围；输出需截断并隐藏敏感变量。首版不具备 OS 级文件系统或网络沙箱，预览必须明确披露这一限制，不能把声明的写入/网络意图描述为已强制隔离。

**完成条件：** 只有人工确认的 reviewed TestPlan 版本可以生成执行预览；计划范围或用例变化后产生新的 draft 版本，旧确认不能授权新版本；每次运行都有唯一 ID；`PASS` 只能来自 `resultTrust=controlled-local`、结果有效且 provenance 与当前任务一致的执行；仅有自然语言摘要的导入记录使用 `status=unknown`、`resultTrust=imported-summary`，不能成为 PASS 证据；失败运行不能被手工改成通过。

**不做：** 不做跨机器分布式执行，不做 CI 云端调度，不做自动质量门禁。

### 12.3 `0.4.0` 证据包、失败分析与回归

**用户价值：** 让测试结果成为可审查的交付证据，并缩小修复后的回归范围。

**输入：** `TestRun`、stdout/stderr、截图、Playwright trace、Git commit、变更文件、历史缺陷。

**输出：** `EvidenceBundle`、失败分析、候选缺陷、`RegressionSet`、回归执行关联。

**核心流程：** `测试失败 → 收集证据 → 分析失败 → 人工确认缺陷 → 计算回归 → 修复后重跑`。

**必须支持：** staging 到只读逻辑证据包的原子 finalize、重复 finalize 幂等、崩溃恢复、证据完整性校验、运行与 commit 绑定、失败步骤/错误摘要、历史缺陷关联、修复前后运行对比。只有状态为 ready 且完整性验证通过的 bundle 可以进入门禁。

**完成条件：** 证据不能脱离终态测试运行单独存在；同一 TestRun 只能有一个 ready bundle；finalizing、孤立目录或完整性失败的 bundle 不能被下载或进入门禁；候选缺陷不能自动成为已确认缺陷；回归项必须能说明来自哪个风险、变更或历史缺陷。

**不做：** 不自动向外部缺陷系统提交，不删除原始 trace/日志，不用 AI 结论替代人工缺陷确认。

### 12.4 `0.5.0` 质量门禁与交付报告

**用户价值：** 根据风险、覆盖、执行结果、证据和未关闭缺陷，给出可解释的交付建议。

**输入：** `QualityTask`、人工决策、`TestRun`、`EvidenceBundle`、`RegressionSet`、未关闭缺陷和发布范围。

**输出：** `QualityGate`、`PASS/WARN/BLOCK`、规则明细、人工接受记录、交付报告和趋势数据。

**核心流程：** `收集事实 → 逐项规则计算 → 汇总结论 → 人工接受例外 → 生成报告`。

**规则底线：** 缺少必需测试证据只能 `WARN` 或 `BLOCK`；存在未接受的 critical 风险必须 `BLOCK`；测试失败且无有效回归结果不能 `PASS`；来源 digest、commit、TestPlan 版本、RegressionSet 版本或 execution profile 版本变化后，旧运行不得满足当前门禁。门禁例外不能覆盖任何 provenance stale、关键测试失败、证据完整性失败或未处置 critical 风险；其他可豁免检查即使被接受，最终结论最高为 `WARN`。人工接受必须记录责任人、理由和期限。

**完成条件：** 同样输入可重算出同样结论；报告可回溯到每个风险、测试运行和证据；规则版本被保存；人工接受不修改原始事实。

**不做：** 不自动发布、不替代审批、不隐藏阻断原因、不允许前端直接提交 `PASS`。

## 15. 风险双状态模型

风险使用两个互不替代的维度：

- `assessmentStatus`：`candidate|confirmed|dismissed`，表示风险是否成立。
- `dispositionStatus`：`open|mitigated|accepted|closed`，表示成立后的处置状态。

`candidate` 风险不能直接进入 `accepted`；`dismissed` 必须有理由；critical/high 风险只有在 `mitigated`、`accepted` 或 `closed` 后才不再阻断 `ready`。人工确认风险成立不等于风险已经处理。
