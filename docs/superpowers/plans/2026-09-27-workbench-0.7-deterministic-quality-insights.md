# Deterministic Quality Insights Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first verifiable 0.7.0 slice: deterministic, evidence-bounded Quality Insights with audited `resolve` and `ignore` decisions, without changing any existing quality primary model or Gate verdict.

**Architecture:** `engine.js` creates a normalized, runtime-field-free project snapshot, computes the full `inputDigest`, and combines pure rule candidates from `rules.js` with per-candidate `scopeDigest` values. Decisions are stored separately as `qualityInsightDecisions`; the HTTP layer re-reads current facts, enforces revision/scope concurrency, writes `qualityAudit`, persists the project, and emits the fixed SSE event only after a successful decision.

**Tech Stack:** Node.js ESM 18+, Node built-in `node:test`, Node `crypto` SHA-256, the existing JSON store, native HTTP/SSE routing, and the existing injected `onBroadcast` test hook.

**Spec:** `docs/superpowers/specs/2026-09-27-workbench-0.7-deterministic-quality-insights-design.md`

## Global Constraints

- Keep the project ESM, Node 18+, and zero production dependencies.
- `RULE_VERSION` is exactly `quality-insight-rules-v1`.
- Rules do not read Store, write project data, call the network, call a model, or recompute a Gate.
- Insight is an explanatory projection; do not duplicate or mutate Requirement, TestCase, TestRun, EvidenceBundle, FailureAnalysis, RegressionSet, Defect, or Gate primary data.
- No PASS, WARN, or BLOCK verdict is generated by the Insight rules; saved computed Gate verdicts remain authoritative.
- `inputDigest` is SHA-256 over the complete normalized snapshot; each Insight gets a digest over only the minimum facts used by that rule.
- `generatedAt` is response metadata only and must not enter any digest, ID, or decision comparison.
- Unknown HTTP request fields are rejected; resolve/ignore must never accept a caller-supplied snapshot or arbitrary Store patch.
- Schema migration is v4 → v5 and initializes `qualityInsightDecisions: []` without dropping unknown or existing fields.
- The slice does not add Auto Review, model calls, UI pages, bilingual UI, automatic defect creation, automatic regression-set mutation, or Gate mutation.

## Review Focus

- Imported summaries and unverified Host summaries must produce an explicit `evidence_gap`, never a positive evidence conclusion; cover this in Task 1's evidence-rule tests.
- A legacy approval Gate must not become a `release_risk`; only saved `kind: 'computed'` Gate verdicts and active risk facts count; cover this in Task 1's Gate tests.
- Missing Evidence IDs in a saved computed Gate must remain in `evidenceRefs` instead of being filtered; cover this in Task 1's evidence-reference test.
- An unrelated project fact must not invalidate a decided Insight, while a related fact must create a new Insight ID/scope; cover this in Task 2's decision and scope tests.
- Stale scope/revision, unknown fields, audit redaction, and exact SSE payload must be observable through the API; cover this in Task 3's API tests.

## File Map

- Create `server/quality/insights/rules.js`: pure candidate rules and the fixed rule version. It receives only the normalized snapshot and returns internal candidates with their minimum rule scope.
- Create `server/quality/insights/engine.js`: snapshot normalization, recursive canonical JSON, SHA-256 digests, deterministic IDs/output ordering, decision overlay, and decision mutation validation. It owns no HTTP side effects.
- Create `server/quality/insights/audit.js`: the narrow quality-insight audit record writer. It records metadata only and never stores a snapshot or log body.
- Modify `server/store.js`: normalize `qualityInsightDecisions` as an array for loaded and newly created projects.
- Modify `server/migrations.js`: advance `CURRENT_SCHEMA_VERSION` from 4 to 5 and initialize the new collection in v4 projects.
- Modify `server/quality/task.js` and `test/helpers/quality-fixtures.js`: provide the same empty-collection fallback for quality normalization and in-memory tests.
- Modify `server/quality/http-routes.js`: add the project query, resolve, and ignore routes, plus audit/persist/event orchestration.
- Modify `test/unit/quality-insights.test.js`: unit tests for snapshot normalization, all five rules, canonicalization, digest scope, ordering, and decision behavior.
- Modify `test/unit/migrations.test.js`: v4 → v5 migration, preservation, and idempotence tests.
- Modify `test/unit/http-api.test.js`: API response, concurrency, audit, mutation-boundary, and broadcast payload tests.

### Task 1: Implement normalized snapshots and deterministic Insight rules

**Files:**
- Create: `server/quality/insights/rules.js`
- Create: `server/quality/insights/engine.js`
- Create: `test/unit/quality-insights.test.js`

**Interfaces:**
- `RULE_VERSION: 'quality-insight-rules-v1'`
- `buildQualitySnapshot(project) -> QualitySnapshot`
- `analyzeQualityFacts(snapshot) -> { insights, inputDigest, generatedAt, ruleVersion }`
- `collectInsightCandidates(snapshot) -> Candidate[]` (the pure rule boundary used by the engine)

`QualitySnapshot` contains only `projectId`, normalized `requirements`, `testcases`, `qualityTasks`, `testruns`, `evidenceBundles`, `failureAnalyses`, `defects`, `regressionSets`, and `gates`. Entity arrays are sorted by ID; `sourceDigests`, `evidenceRefs`, `reasonRefs`, and `testCaseIds` are lexicographically sorted; Gate checks are sorted by `key`. Omit timestamps, artifact paths, temporary directories, raw logs, and other runtime-only fields while preserving missing evidence references.

- [ ] **Step 1: Write the failing unit tests for all five rule families and determinism**

Add named tests that assert:

  - `requirement_gap` is emitted for a requirement whose normalized description or acceptance is empty, while `coverage_gap` uses only valid `requirement.links[].testcaseId` references and ignores a text-only TestCase `trace`.
  - `evidence_gap` is emitted for every terminal TestRun (`passed`, `failed`, `cancelled`, `timed-out`, `environment-error`) without a matching `testRunId` + `state: 'ready'` + `integrity: 'verified'` EvidenceBundle; `imported-summary` and Host evidence with mismatched host provenance do not satisfy the rule.
  - A computed Gate with a missing evidence ID preserves that ID in the resulting `evidenceRefs`; an approval Gate is ignored by both `evidence_gap` Gate checks and `release_risk`.
  - `regression_gap` selects the highest eligible `manual`/`calculated` set for each quality task, breaks equal versions by the smallest ID, and reports missing `risk:<id>`/`defect:<id>` references for active risks/defects. A project-level manual set with an empty `qualityTaskId` is not auto-bound.
  - `release_risk` uses a saved computed `BLOCK`/`WARN` verdict without calling Gate evaluation, and maps BLOCK/critical to `high`, WARN-only to `medium`; it reports active critical/high risks even when no Gate is present.
  - Two snapshots with recursively reordered object keys and semantically reordered sets have equal `inputDigest`, equal scope digests, equal IDs, and equal sorted output. `undefined` object values are omitted, `reason.args` is recursively canonicalized, and exact duplicate candidate tuples are emitted once.
  - Changing an unrelated entity changes the full `inputDigest` but leaves an unaffected Insight's `scopeDigest` and ID unchanged; changing a fact used by that Insight changes both.

Use `makeProject`, `makeQualityTask`, `makeTestRun`, `makeEvidenceBundle`, and `makeGate` from `test/helpers/quality-fixtures.js`; keep rule tests independent of HTTP and real files.

- [ ] **Step 3: Implement `collectInsightCandidates(snapshot) -> Candidate[]` in `server/quality/insights/rules.js`**

Implement exactly five rules: `requirement_gap`, `coverage_gap`, `evidence_gap`, `regression_gap`, and `release_risk`. Each candidate contains only `{ kind, target: { type, id }, reason: { code, args }, evidenceRefs, severity, scope }`; `scope` is internal input for the engine and is never returned in the public Insight. Use stable reason codes and JSON-safe arguments:

  - `requirement_gap`: normalized description/acceptance missing; target the requirement; severity `medium`.
  - `coverage_gap`: no valid linked TestCase; target the requirement; severity `medium`.
  - `evidence_gap`: target the affected run or computed Gate; severity `high`; a controlled Host run additionally requires matching `hostExecutionId` and `hostResultDigest`; never treat imported summaries as controlled evidence.
  - `regression_gap`: target the quality task (or the selected regression set when the set exists); include missing active risk/defect references in `reason.args`; severity `high` when an active critical/high risk exists, otherwise `medium`.
  - `release_risk`: target the computed Gate for a saved BLOCK/WARN, or the quality task/project for active critical/high risk; do not inspect or recalculate legacy approval verdicts; use only `high` for BLOCK/critical and `medium` for WARN-only.

Use the spec's activity definitions: a risk is active unless dismissed and unless its disposition is `mitigated`, `accepted`, or `closed`; a defect is active unless its status is `closed` or `verified`.

Use these fixed reason codes and argument shapes so rule output is stable across
locales: `missing-requirement-fields { fields }`, `no-valid-testcase-link { traceOnly }`,
`missing-verified-evidence { runId, resultTrust }`, `invalid-evidence-reference { checkKey, missingRefs }`,
`missing-regression-set { qualityTaskId }`, `regression-coverage-gap { qualityTaskId, setId, missingRiskRefs, missingDefectRefs }`,
`computed-gate-blocked { gateId, verdict }`, `computed-gate-warning { gateId, verdict }`, and
`critical-risk-open { qualityTaskId, riskIds }`. Arrays in every argument object are sorted.

- [ ] **Step 4: Implement `buildQualitySnapshot(project) -> QualitySnapshot` in `server/quality/insights/engine.js`**

Normalize Requirement description as the first non-empty value of `description`, `statement`, and `summary`; normalize acceptance as `acceptanceCriteria` then `acceptance`. Keep only the rule-needed fields from each entity, retain invalid evidence IDs, and copy data so analysis cannot mutate the project. Keep non-set arrays in their semantic order and sort only the collections pinned by the spec.

- [ ] **Step 5: Implement canonicalization, digests, IDs, dedupe, and output ordering in `engine.js`**

Recursively sort object keys, omit `undefined` object properties, preserve already-normalized non-set array order, and serialize the canonical value with JSON before SHA-256 hashing. Compute `inputDigest` from the complete snapshot. For each candidate compute `scopeDigest` from `scope`, then form the Insight ID from `{ ruleVersion, scopeDigest, kind, target, reason, evidenceRefs }`. Remove the internal scope, set `status: 'open'` and `revision: 0`, and sort Insights by severity `high → medium → low`, kind, target type, target ID, reason code, and ID. Deduplicate exact `{ kind, target, reason, evidenceRefs }` tuples before final sorting.

- `ignoreInsight(project, insightId, { expectedRevision, scopeDigest, actorLabel, reason }) -> decision`
- `QualityInsightError` exposes one of `QUALITY_INSIGHT_NOT_FOUND`, `QUALITY_INSIGHT_STALE`, `QUALITY_REVISION_CONFLICT`, `QUALITY_INSIGHT_ALREADY_DECIDED`, `QUALITY_INSIGHT_ACTOR_INVALID`, or `QUALITY_INSIGHT_REASON_INVALID` through `.code`.
- `appendQualityInsightAudit(project, fields) -> auditRecord`

The decision collection is `project.qualityInsightDecisions`. A fresh Insight has public revision `0`; a successful first decision creates one record at revision `1`. The engine may mutate only this collection and must not persist, broadcast, touch the project, or alter any primary quality entity; the HTTP route owns those side effects.

- [ ] **Step 1: Write failing decision and migration tests**

Add tests that assert:

  - `migrateDb` converts schema v4 to v5, initializes `qualityInsightDecisions: []`, preserves existing quality collections and unknown fields, and is idempotent.

  - `mergeQualityInsightDecisions` overlays one matching decision as `resolved` or `ignored` with revision `1` without changing the current analysis digest.
  - The first resolve/ignore stores the current full `inputDigest`, current `scopeDigest`, actor, reason, and timestamps; a second decision for the same Insight is rejected with `QUALITY_INSIGHT_ALREADY_DECIDED`.
  - A mismatched expected revision is rejected with `QUALITY_REVISION_CONFLICT`; a changed scope is rejected with `QUALITY_INSIGHT_STALE`; missing actor/reason is rejected; missing current Insight is `QUALITY_INSIGHT_NOT_FOUND`.
  - An unrelated fact change keeps the current Insight ID/scope and merged decision, while a related fact change yields a new Insight ID and does not reuse the old decision.
  - Gate objects and all other project quality arrays are byte-for-byte unchanged after a decision mutation.

### Task 3: Expose query/resolve/ignore APIs with audit and SSE contracts

**Files:**
- Modify: `server/quality/http-routes.js`
- Modify: `test/unit/http-api.test.js`

**Interfaces:**
- `GET /api/projects/:projectId/quality-insights -> { ok, inputDigest, ruleVersion, generatedAt, insights }`
- `POST /api/projects/:projectId/quality-insights/:insightId/resolve` accepts exactly `{ expectedRevision, scopeDigest, actorLabel }`.
- `POST /api/projects/:projectId/quality-insights/:insightId/ignore` accepts exactly `{ expectedRevision, scopeDigest, actorLabel, reason }`.
- Successful mutation returns HTTP `200` with `{ ok: true, insight, decision }`.
- Successful mutation emits `quality.insight.updated` with exactly `{ projectId, insightId, status, revision, inputDigest, scopeDigest, updatedAt }`.

- [ ] **Step 1: Add failing API tests for query, mutation, error, audit, and broadcast behavior**

Extend the existing HTTP test bootstrap with an `events` array through `startQaBench({ onBroadcast })`. Add tests that assert:

  - GET returns the current deterministic snapshot result and merged decision status, does not create a decision, and does not change the data-file mtime.
  - Unknown request fields return `400`; missing project returns `404`; current-missing Insight returns `404` with `QUALITY_INSIGHT_NOT_FOUND`.
  - stale `scopeDigest`, stale `expectedRevision`, and a repeated decision return `409` with the exact stable codes from the spec.
  - resolve and ignore return `200` with the current Insight plus decision; ignore requires non-empty actor and reason.
  - success writes the fixed `qualityAudit` fields, persists only `qualityInsightDecisions`/audit metadata, leaves Gate/Evidence/RegressionSet/Defect facts unchanged, and emits the exact `quality.insight.updated` payload once.
  - domain rejections after project/Insight lookup append a redacted audit record with `result: 'rejected'` and the stable `errorCode`; no raw snapshot or log string appears in serialized audit data.

A rejected domain mutation persists its audit record but never modifies a Gate or emits a success event. Do not create Defect, RegressionSet, EvidenceBundle, or Gate records.
