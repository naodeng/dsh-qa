# DSH QA Workbench 0.7.0 Deterministic Quality Insights Design

状态：待用户审阅

## 1. 目标与共同理解

0.7.0 的主题是 Evidence-first 的 AI Quality Intelligence。本 spec 只定义
0.7.0 的第一条可验证切片：从项目中已经保存的质量事实生成确定性的
Quality Insight，并允许测试人员对 Insight 做带 revision 和审计的
`resolve` / `ignore` 决策。

目标用户是使用 dsh-qa 管理测试范围、执行、证据和质量门禁的 QA 或测试负责人。
这条切片要解决的问题是：现有事实分散在 Requirement、TestCase、TestRun、
EvidenceBundle、FailureAnalysis、RegressionSet 和 Gate 中，用户需要看到
可解释的缺口，但不能把推测当事实，也不能让 Insight 绕过既有质量门禁。

成功标准：

- 同一份事实快照产生相同的 `inputDigest`、`scopeDigest`、Insight ID 和规则结果。
- 每条 Insight 都能说明目标、原因、证据引用和规则版本。
- 人工决策需要操作者、理由（`ignore` 必填）和 `expectedRevision`。
- 与 Insight 相关的事实变化会使旧 Insight 失效；无关事实变化不会让所有 Insight
  的决策同时失效。
- Insight 不修改 Gate、Evidence、FailureAnalysis、RegressionSet 或 Defect 主模型。
- 没有证据时明确呈现证据缺口，不生成正向质量结论。

## 2. 范围

### 2.1 本切片包含

- `server/quality/insights/rules.js`：纯确定性规则。
- `server/quality/insights/engine.js`：快照规范化、digest、规则编排、Insight 合并。
- 独立的 `qualityInsightDecisions` 决策集合。
- 项目级 Insight 查询、resolve 和 ignore API。
- schema v4 → v5 migration 和旧项目的空集合兼容。
- Node unit、API 和 migration 测试。

### 2.2 本切片不包含

- DSH Auto Review 或任何模型调用。
- Failure category、RegressionSet 或 Gate recommendation 的自动生成。
- 前端 Insight 页面、双语 UI 或新的导航入口。
- 自动创建缺陷、自动修改回归集或自动修改 Gate。
- Quality Obligation、Evidence Graph、Agent Loop 和多 Agent 编排。

这是一条 0.7.0 的基础子项目，不把本切片单独宣称为完整的 0.7.0 Release。

## 3. 架构

```text
项目已保存的质量事实
        |
        v
规范化 Quality Snapshot
        |
        v
稳定 inputDigest
        |
        v
Deterministic Insight Rules
        |
        v
当前 Quality Insights
        |
        +---- 合并 qualityInsightDecisions
        |
        v
只读响应 / 人工 resolve 或 ignore
```

### 3.1 `rules.js`

规则模块不读取 Store、不写入项目、不调用网络或外部工具。每个规则接收
规范化快照并返回候选 Insight。规则输出不依赖当前时间，也不重新计算 Gate。

规则版本固定为 `quality-insight-rules-v1`。Insight 的 `reason` 使用
`{ code, args }`，不把单一语言的自然语言文案写入领域事实。

### 3.2 `engine.js`

引擎提供以下边界：

```js
buildQualitySnapshot(project) → snapshot
analyzeQualityFacts(snapshot) → {
  insights,
  inputDigest,
  generatedAt,
  ruleVersion,
}
resolveInsight(project, insightId, options) → decision
ignoreInsight(project, insightId, options) → decision
```

`analyzeQualityFacts` 是纯分析入口。`generatedAt` 只用于响应元数据，不进入
digest。项目路由先生成当前快照，再把 `qualityInsightDecisions` 合并到结果中。
`resolveInsight` 和 `ignoreInsight` 的 `options` 只允许
`expectedRevision`、`scopeDigest`、`actorLabel` 以及 `ignore` 使用的 `reason`；
它们必须重新读取当前项目事实并校验当前 Insight，不能接受调用方提交的快照或
直接接收任意 Store patch。校验失败使用本 spec 定义的稳定错误码。

### 3.3 决策集合

Insight 是事实的解释性投影，不作为 Requirement、Evidence 或 Gate 的第二份主数据。
项目只持久化人工决策：

```js
{
  id,
  insightId,
  inputDigest,
  scopeDigest,
  status: 'resolved' | 'ignored',
  revision: 1,
  actorLabel,
  reason,
  createdAt,
  updatedAt,
}
```

`scopeDigest` 是 resolve/ignore 的并发边界；完整 `inputDigest` 只作为分析和审计
provenance 保存，不会因为无关项目事实变化而使该决策过期。

同一个 `insightId` 最多有一个决策记录。首次决策的公开 revision 为 `0`；成功
决策后记录 revision 为 `1`。已经决策的 Insight 不允许通过本切片反向切换状态；
与该 Insight 相关的事实变化后会产生包含新 `scopeDigest` 的新 Insight ID。

## 4. 规范化快照与稳定性

快照只包含规则需要的稳定字段：

```js
{
  projectId,
  requirements,
  testcases,
  qualityTasks,
  testruns,
  evidenceBundles,
  failureAnalyses,
  regressionSets,
  gates,
}
```

规范化要求：

- 将 `acceptance` 和 `acceptanceCriteria` 统一为可判断的验收标准状态。
- 将 `requirements[].links[].testcaseId` 统一为需求到用例的有效关联。
- 保留 `testcase.trace` 作为未验证追踪信息；只有有效关联才算覆盖，不把任意文本
  trace 当作已验证关系。
- 风险从质量任务中提取，并保留风险 ID、严重级别、评估状态和处置状态。
- TestRun、EvidenceBundle、FailureAnalysis、RegressionSet 和 Gate 只保留规则所需
  的 ID、状态、版本、provenance、evidenceRefs 和关系字段。
- 所有 ID 集合和可排序数组按稳定顺序排序；去除时间戳、artifact 路径、临时目录、
  原始日志和其他运行时字段。
- 证据引用即使不存在也要保留，不能在规范化时静默删除。

`inputDigest` 使用 SHA-256 对完整规范化快照的 canonical JSON 计算，用于本次分析
的整体 provenance。每条规则再从它实际读取的最小事实集合计算 `scopeDigest`；规则
不得把整个项目快照作为所有 Insight 的共同 scope。Insight ID 使用
`ruleVersion`、`scopeDigest`、规则 kind、target、reason 和排序后的 `evidenceRefs`
计算，因此无关事实变化不会使其他 Insight 的决策失效。

canonical JSON 的规则固定为：对象 key 递归按字典序排序；`undefined` 不进入输入；
数组由规范化步骤按其语义排序，非集合数组保持顺序；`reason.args` 必须是 JSON-safe
值并经过同样的递归规范化。Insight 输出按 `severity`（high → medium → low）、
`kind`、`target.type`、`target.id`、`reason.code`、`id` 排序；完全相同的
`kind + target + reason + evidenceRefs` 只保留一条。

项目级实体数组按 `id` 排序；`sourceDigests`、`evidenceRefs`、`reasonRefs` 和
`testCaseIds` 按字典序排序；Gate checks 按 `key` 排序；风险按 `id` 排序。保留
字段的空字符串和 `null` 语义由规则规范化器固定，不允许由调用顺序决定。

## 5. 首批确定性规则

所有规则都只生成缺口或风险类 Insight，不生成 PASS、WARN 或 BLOCK verdict。

| kind | 触发条件 | target | 证据边界 |
| --- | --- | --- | --- |
| `requirement_gap` | 需求缺少描述或验收标准 | requirement | 缺少有效 Evidence 时保持空引用 |
| `coverage_gap` | 需求没有关联到有效测试用例 | requirement | 文本 trace 不等于有效覆盖 |
| `evidence_gap` | 任意终态运行缺少匹配的 `ready + verified` Evidence；`imported-summary` 或未经验证的 Host summary 不能满足受控证据要求；或保存的 computed Gate 引用缺失/失效证据 | run、evidence 或 gate | 缺失的原始引用保留在 `evidenceRefs`；默认 high |
| `regression_gap` | 对每个质量任务，当前回归集未引用活动风险/缺陷，或没有可用回归集 | quality task 或 regression set | 不自动创建或修改回归集；存在 critical/high 风险时 high，否则 medium |
| `release_risk` | `kind: 'computed'` 的已保存 Gate 为 `BLOCK`/`WARN`，或存在未处置的 high/critical 风险 | gate、quality task 或 project | 读取保存的 verdict，不重新计算 Gate；BLOCK 或 critical 风险为 high，单独 WARN 为 medium |

Insight 结构：

```js
{
  id,
  kind,
  target: { type, id },
  reason: { code, args },
  evidenceRefs: [],
  severity: 'high' | 'medium' | 'low',
  status: 'open' | 'resolved' | 'ignored',
  inputDigest, // 本次完整快照 digest
  scopeDigest, // 当前规则实际读取的最小事实 digest
  ruleVersion,
  revision,
}
```

没有可用证据时 `evidenceRefs` 为空，且原因必须表达证据缺口。

`regression_gap` 的选择规则固定为：对每个 `qualityTask`，只考虑
`regressionSet.qualityTaskId === qualityTask.id` 且状态为 `manual` 或 `calculated`
的集合；选择最高 `version`，版本相同时选择 ID 字典序最小的集合。集合必须通过
`reasonRefs` 中的 `risk:<id>` / `defect:<id>` 表达覆盖；缺少引用不能推断已覆盖。
`qualityTaskId` 为空的项目级手工集合不自动绑定到任意质量任务。活动风险的定义为
未 dismissed 且 disposition 不是 `mitigated`、`accepted` 或 `closed`；活动缺陷为
状态不属于 `closed` / `verified`。

本切片不实现 `automation_gap`：当前 TestCase 写入路径没有稳定的
`automationRequired` 字段来源，不能仅在 fixture 中制造一个生产模型不存在的规则。
待该字段进入正式数据契约后再加入规则和对应迁移。

## 6. API 与人工决策

### 6.1 查询

```text
GET /api/projects/:projectId/quality-insights
```

查询实时读取项目事实并返回：

```js
{
  ok: true,
  inputDigest,
  ruleVersion,
  generatedAt,
  insights,
}
```

查询不写 Store，不创建决策记录，不改变 Gate 或其他质量实体。

### 6.2 Resolve

```text
POST /api/projects/:projectId/quality-insights/:insightId/resolve
```

请求字段只能是：

```js
{
  expectedRevision,
  scopeDigest,
  actorLabel,
}
```

服务端确认当前 digest、Insight ID 和 revision 后写入 `resolved` 决策。

### 6.3 Ignore

```text
POST /api/projects/:projectId/quality-insights/:insightId/ignore
```

请求字段只能是：

```js
{
  expectedRevision,
  scopeDigest,
  actorLabel,
  reason,
}
```

`actorLabel` 和 `reason` 必须是非空字符串。

### 6.4 错误与事件

- 项目不存在：`404`。
- Insight 不存在于当前快照：`404 QUALITY_INSIGHT_NOT_FOUND`。
- `scopeDigest` 已变化：`409 QUALITY_INSIGHT_STALE`。
- revision 不匹配：`409 QUALITY_REVISION_CONFLICT`。
- Insight 已有终态决策：`409 QUALITY_INSIGHT_ALREADY_DECIDED`。
- 未知请求字段、操作者或理由无效：`400`。
- 成功决策返回 `200`：`{ ok: true, insight, decision }`。
- 成功决策发送 `quality.insight.updated`，payload 固定为
  `{ projectId, insightId, status, revision, inputDigest, scopeDigest, updatedAt }`，
  并更新项目活动时间。
- 成功决策和已定位到项目/Insight 后的领域拒绝都写入 `qualityAudit`：
  `entityType: 'quality-insight'`、`entityId`、`action`、`source: 'http'`、
  `actorLabel`、`fromRevision`、`toRevision`、`result`、`errorCode`、`reason`、
  `inputDigest`、`scopeDigest`、`createdAt`、`at`。审计不保存原始快照或日志正文。

决策函数和路由都不得调用 Gate 写入逻辑，也不得创建 Defect、RegressionSet 或
EvidenceBundle。

## 7. 存储迁移与兼容

- `CURRENT_SCHEMA_VERSION` 从 `4` 升至 `5`。
- v4 → v5 为每个项目初始化 `qualityInsightDecisions: []`。
- `store.normalizeProject` 和质量 fixture 同时提供空数组兜底，保证内存 fixture、
  旧项目和动态导入测试都能读取。
- 不修改已有 Requirement、TestCase、TestRun、Evidence、Gate 或历史审计字段。

## 8. 验证策略

### 8.1 Unit

- 五类规则分别覆盖命中、不命中和信息不足场景；包括 imported summary、legacy
  approval Gate、computed Gate、活动风险/缺陷和回归集选择。
- 同一快照重复分析得到相同 `inputDigest`、`scopeDigest`、Insight ID 和排序结果；
  递归 key 排序、输出排序和重复 Insight 去重都有测试。
- Gate 缺失证据引用不会被过滤。
- 无关事实变化不会使其他 Insight 的 scopeDigest 或已保存决策失效；相关事实变化
  会返回新的 Insight ID。
- 首次 resolve/ignore、重复决策、缺少 actor/reason、过期 revision 和过期 scopeDigest。
- Gate verdict 在所有 Insight 决策前后保持不变。

### 8.2 API

- 查询返回当前快照和合并后的决策状态，且不产生 Store 写入。
- resolve/ignore 的字段白名单、404、409、审计和 SSE 事件。
- resolve/ignore 成功响应和 `quality.insight.updated` payload 与本 spec 一致。
- 决策不会修改主质量实体或创建第二套 Gate 结果。

### 8.3 Migration 与交付门槛

- v4 数据迁移到 v5 后保留原字段并初始化决策集合。
- 运行 `npm run test:unit`。
- 运行 `npm test`，确认既有 Chromium E2E 不回归。
- 运行 `git diff --check`。

## 9. 后续衔接

本切片完成后，0.7.0 后续工作可以复用 `inputDigest`、Insight schema、证据引用和
人工决策边界接入 Auto Review。Auto Review 必须作为不可信输入经过独立 schema
校验，不能改变本 spec 中的 Gate、Evidence 和人工确认边界。
