# 研发质量控制 Preset 设计

> 状态：已确认设计，面向 dsh-qa 的可安装 DSH 用户 preset。

## 目标

提供一个 `quality-control` preset，让同一个 DSH 会话可以按显式角色和研发阶段，从不同专业视角审视完整研发流程，并输出可追溯、可交接、可人工复核的质量意见与建议。

## 设计依据

- `awesome-qa-prompt`：输入审计、禁止编造、最小可执行输出、事实与假设分离。
- `awesome-qa-skills`：阶段 Skill、角色视角 Skill、多角色质量汇总、来源追踪、冲突保留、人工最终决定。
- `AI-Quality-Workforce`：研发质量 Loop、Artifact 版本交接、质量门禁、阶段与 Task 分层、角色按风险参与。

## 角色视角

| 角色 | 关注点 | 权限边界 |
|---|---|---|
| BA | 业务目标、规则、流程、验收条件、需求可测试性 | 不替产品确认未经证实的业务意图 |
| PM | 范围、优先级、资源、依赖、里程碑和行动 | 不覆盖质量事实、缺陷状态或风险结论 |
| Product | 用户价值、范围、验收标准、产品风险 | 不替技术确认实现正确性 |
| QA | 可测试性、风险覆盖、用例、缺陷、执行证据和质量风险 | 无执行证据不得宣称通过或可发布 |
| Developer | 实现、代码质量、单元测试、技术债和变更影响 | 不把静态阅读当作运行验证 |
| Tech Lead | 架构、接口、数据、性能、安全、可观测性和可维护性 | 不替人工做发布或风险接受决定 |
| Automation | 自动化分层、稳定性、数据、断言、CI 和维护成本 | 不虚构可运行环境和执行结果 |
| UX | 信息架构、交互、可用性、无障碍和跨端体验 | 不替产品确认业务优先级 |
| Security | 威胁面、权限、数据暴露、依赖和安全验证证据 | 不输出未经验证的合规结论 |
| DevOps/SRE | 构建、部署、环境、监控、回滚和运行风险 | 不把部署成功等同于质量通过 |
| Data | 数据模型、一致性、埋点、指标、报表和数据验证 | 不编造指标目标或数据结论 |
| Release | 发布条件、阻塞项、变更影响、回滚和剩余风险 | 不代替授权人批准发布 |

## 默认研发质量阶段

1. 需求与业务质量
2. 技术方案与架构质量
3. 测试策略与计划
4. 测试用例与验收设计
5. 开发实现与代码评审
6. 构建、环境与测试执行准入
7. 功能与专项测试
8. 缺陷、修复与回归
9. 测试结果与质量报告
10. 发布质量评估

用户可以指定单个阶段，也可以要求从多个角色对整个流程做端到端质量分析。未指定角色时，preset 先推荐最小角色组合并说明理由，不静默伪造角色参与。

## 统一交付协议

每份角色意见至少包含：`role`、`stage`、`scope`、`source_id`、`input_versions`、`facts`、`evidence`、`findings`、`risks`、`gaps`、`recommendations`、`confidence` 和 `human_decisions`。

汇总时必须保留来源、版本、冲突、少数高风险发现、未参与角色及其覆盖缺口。计划、代码阅读、角色判断和建议不能被写成已执行事实。没有执行证据时，整体状态只能是“未执行或证据不足”。

## 非目标

- 不复制两个仓库的完整 Skill 或 Prompt 内容。
- 不机械创建每个角色 × 每个阶段的独立 Agent。
- 不自动修改研发流程规则、Skill、Prompt 或项目业务数据。
- 不替代人工审批、发布、风险接受、豁免和合规决策。
