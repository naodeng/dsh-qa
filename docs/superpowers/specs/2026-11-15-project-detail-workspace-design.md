# 项目详情工作区交互设计

## 设计意图

把项目详情从“在窄面板里浏览一串记录”改成一个有明确入口、导航和任务上下文的项目工作区。用户打开项目后，应该能先判断当前质量状态，再沿着需求、用例、执行、证据和交付路径查看细节，不必在多组互不相连的列表之间来回切换。

本设计落实已选方向 **A：项目工作区**。它采用完整项目页面作为主结构，嵌入需求—用例追溯矩阵，并把质量任务作为贯穿执行流程的工作队列。

## 当前体验与问题

- 项目卡片的“快速预览”打开的是项目快照抽屉；它适合看摘要，不适合承载大量需求、步骤、执行结果和证据。
- 应用已经有独立的项目详情视图，但页面主体仍呈现为内嵌的圆角卡片，内容以十个并列标签和分开的记录列表为主。需求与用例关联存在于数据里，界面上却难以快速看出覆盖缺口、验证点和后续行动。
- 质量任务、执行配置、测试运行、证据包、缺陷、报告分别呈现，用户需要自己拼出“现在卡在哪里、下一步做什么”。
- 详情页与快速预览都提供项目层级信息，职责不够清楚；进入详情的动作和返回原工作位置也需要更直接。

## 目标

1. 明确快速预览与完整详情的分工，减少在预览中找不到信息的情况。
2. 让完整详情占据应用主内容区，视觉和滚动行为都像一页工作区，不再像另一个浮层卡片；先看状态与行动，再看需求覆盖、执行质量和交付材料。
3. 将需求和关联用例放在同一追溯视图，支持从需求展开到用例的前置条件、步骤、预期结果及现有执行/证据上下文。
4. 把质量任务变为可识别、可继续处理的工作入口，同时保留质量门禁与证据的可信边界。
5. 桌面和窄屏都能完成项目浏览、跳转、展开和返回，不依赖半屏面板容纳完整内容。

## 非目标

- 不重做首页、项目看板、工作日历、DSH 对话等主页面的整体视觉语言。
- 不创建第二套项目、需求、用例、执行、证据或门禁数据模型。
- 不创建新的后端资源、持久化字段或行动项判定规则；可在现有 Action Queue 查询中增加项目过滤参数，以复用已有事项与排序。
- 不把 AI 建议、导入的运行摘要或未经校验的宿主返回直接呈现为通过门禁的事实。

## 方案比较与决策

| 方案 | 核心结构 | 优点 | 取舍 |
| --- | --- | --- | --- |
| **A. 项目工作区（选定）** | 全页项目工作区；项目概况、追溯、质量任务、缺陷风险、证据交付和时间线分区 | 能容纳完整上下文，也让不同阶段沿同一项目导航；适合项目负责人日常工作 | 需要重新组织现有详情内容，而非只改抽屉尺寸 |
| B. 追溯矩阵优先 | 页面主体以需求—用例覆盖矩阵为中心，其他内容通过侧栏或检查器打开 | 对验收覆盖检查很直接 | 项目状态、任务和交付仍显得次要；作为所有项目详情的入口过窄 |
| C. 质量任务优先 | 以当前任务队列和下一步动作为主体，按任务打开需求、执行和证据 | 适合按任务推进执行 | 对以需求或交付审查为入口的用户不够平衡，项目全貌较难扫描 |

选择 A。追溯矩阵采用 B 的可扫描与可展开做法；质量任务区吸收 C 的“待处理项—当前上下文—下一步”组织方式。它们是工作区内的重点区域，不取代整个项目的信息架构。

## 信息架构

```text
项目详情
├── 项目头部：标题、项目键、阶段、负责人、被测产品、返回、DSH 对话、项目文件
├── 项目导航
│   ├── 项目概况
│   ├── 需求与用例
│   ├── 质量任务
│   ├── 缺陷与风险
│   ├── 证据与交付
│   └── 动态与排期
└── 当前分区
```

“里程碑与日程”“知识沉淀与会议纪要”“质量门禁”“执行配置、测试计划和运行”放进最相关的分区，避免继续以十个并列标签争夺一级导航：

- **项目概况**：项目阶段和摘要、需关注事项、需求/用例/开放缺陷/已验证证据数量、最近质量信号、临近里程碑；原有项目信息编辑、协作策略、工作目录和删除操作仍可到达。
- **需求与用例**：需求—用例追溯矩阵、未关联用例、覆盖筛选与展开详情。
- **质量任务**：任务列表、真实任务阶段、验收标准、风险、测试范围、分析决策、执行配置和执行记录。与任务/运行关联的故障分析、回归集显示在相关任务上下文；无法归属到任务的项目级记录仍在本分区的项目资源列表中可访问。
- **缺陷与风险**：开放缺陷、严重程度、影响、复现信息，以及质量任务中的未关闭风险入口。
- **证据与交付**：证据包状态和完整性、可查看/下载材料、报告版本、质量门禁及审批结果。
- **动态与排期**：分别呈现近期动态、未来里程碑/日程，以及知识沉淀和会议纪要；过去活动与未来安排不得混为同一条无方向的时间线。

若现有数据不支持某种汇总，只展示可追溯来源的事实，不造新状态。项目概况的“需关注”链接必须跳转到对应实体和分区。

## 主要交互

### 入口与预览

1. 项目卡片主体点击进入完整项目详情；“快速预览”保持为单独入口。
2. 快速预览只显示项目名、项目键、阶段、负责人/产品、简短质量摘要和最近活动，并提供明确的“进入完整详情”主按钮。
3. 预览不再放置多分区导航、长用例步骤、完整证据列表或需要连续操作的工作流。关闭预览后回到原列表位置。
4. 完整项目详情的返回按钮返回打开它的来源视图（首页、看板或 DSH 对话），并保留原有项目选择与滚动上下文。

### 项目概况

- 页面顶部保留项目标题与关键元信息，主要动作位于右侧或窄屏的“更多操作”菜单。主内容区不再套一层有边框、圆角、阴影和内置滚动的浮层卡片；项目导航和当前分区在应用页面内展开。
- 首屏依次展示阶段/质量摘要、需要处理的项目和关键计数。避免用一组数字卡片代替行动说明。
- “需要处理”复用 Action Queue 已有事项，不在前端另造规则；只展示当前项目中 `actionRequired` 为真或状态为 `blocked` 的事项，按 Action Queue 现有优先级、是否需要操作、状态、截止时间和稳定 ID 顺序排列。首屏先展示前五条，可展开本次项目查询返回的其余事项（当前接口最多返回 50 条）。正在运行等 `in_progress` 监控项单独显示，不算作待处理动作。
- Action Queue 加载失败或项目过滤结果不完整时显示错误/刷新状态，不能把它伪装成“没有待处理事项”；只有成功取回项目范围内结果后才显示空状态。
- 点击需求、缺陷、证据和门禁计数时，跳至对应分区并应用合理的默认筛选。

### 需求—用例追溯

- 采用**需求为行、用例为可展开关联内容**的表格。桌面端优先使用固定表头和横向空间；小屏改为需求卡片，保留同样的信息顺序。
- 默认列：需求标识/标题、验收要点、关联用例数及状态分布、覆盖状态、风险/优先级。默认不把无来源的“逐用例执行通过/失败”塞进矩阵。
- 覆盖摘要使用单一主状态并允许附加异常计数，优先级固定为：有失效关联或未知/缺失状态时主状态为“需核对”；否则没有有效关联时为“无覆盖”；否则任一关联用例为 `draft` 时为“待评审”；只有所有关联用例均为 `reviewed` 或 `executed` 时才是“已评审覆盖”。异常出现时仍展示有效关联数、草稿数、未知状态数和失效关联数，不丢弃次级信息。仅把能解析到现有用例记录的链接作为有效关联；指向不存在用例的每条链接记录单独计为失效关联。重复的 `testcaseId` 按一个用例计数，但展开后保留各条 `links[].purpose` 验证点。`executed` 在此仍只代表用例登记状态，不代表运行结果；覆盖摘要不是质量门禁结论。
- 展开某条需求后，直接显示其关联用例。每个用例可继续展开前置条件、步骤、预期结果、类型、优先级和风险；收起后仍保留当前筛选与滚动位置。
- 关联用例展示 `links[].purpose` 作为“验证点”，提供从用例回看关联需求的入口。未关联用例单列在矩阵末尾，避免遗漏。
- 提供标题/标识搜索和覆盖状态筛选（全部、无覆盖、待评审、已评审覆盖、需核对）。筛选结果为空时给出清除筛选动作。
- 表格中的状态操作沿用现有用例状态能力；需求/用例详情中没有的编辑或关联维护操作不在本轮新增。
- 当前 TestRun 主要保存项目级状态与摘要，不代表每条用例的执行结果。只有在已有数据明确包含用例级结果时才展示在用例明细；否则显示“暂无逐用例执行结果”，并链接到项目运行摘要，不能推断为通过或失败。

### 质量任务与执行

- 质量任务列表先显示有待确认风险等行动项的任务，再将其余任务按更新时间倒序排列；行内展示当前数据里的真实 `stage`、风险/阻塞和更新时间。当前模型没有通用的“进行中/已完成”生命周期，界面不得推导或分组展示这类状态。
- 选中任务后在当前分区打开任务详情；先显示验收标准、风险和测试范围，再显示来源快照/分析决策、计划、执行配置、运行记录和相关证据。未关联到质量任务的项目级运行或分析记录通过明确的“项目级记录”列表保留入口。
- 任务主操作基于其真实状态提供，例如继续补充信息、查看计划、预览并执行、查看运行结果。当前无可执行操作时不显示伪按钮。
- Host 执行仍要求预览与用户确认；取消、重试沿用现有服务端状态和审计语义。宿主返回不直接变成 PASS，证据需要服务端完成校验。
- 用户从首页行动项、项目概况、追溯矩阵或缺陷进入质量任务时，均能看到一致的任务信息和明确的返回路径。

### 缺陷、证据、交付与活动

- 缺陷与风险按开放优先，提供严重程度、状态和影响的快速扫描；行内展开复现步骤、预期/实际和可用证据。
- 证据与交付按“门禁结论 → 报告 → 证据包”组织。每个结论标明来源、状态和可执行动作；已校验证据可打开/下载，校验中/失败/过期状态要清楚区分。
- 近期动态使用项目当前可用的活动材料和阶段变更，按时间倒序展示；只在记录能稳定定位到实体时提供跳转。当前项目材料列表最多保留六条摘要，因此此区域称为“近期动态”，不宣称为完整审计历史，也不补造缺失的历史关联。
- 未来里程碑与日程使用独立的排期列表，按截止/发生时间排列；知识沉淀和会议纪要保留独立列表入口，避免被近期动态的条数限制隐藏。
- 门禁审批仍由负责人明确执行，并保留既有确认、通过/驳回记录和权限语义。

## 响应式与可访问性

- 桌面：项目详情占满应用主内容区；左侧项目导航宽度稳定，主页面整体滚动，不在圆角卡片/抽屉内再做一层受限滚动。追溯表格优先压缩非关键列，展开内容不再套入第二个小视窗。
- 窄屏：顶部项目身份与主动作保持可见；导航转成可横向滚动的分区选择器；追溯矩阵转换为需求卡片和逐层展开；操作菜单收进单一入口。
- 快速预览在窄屏以接近全屏的抽屉/对话层呈现，但仍是精简快照，并保留全页详情入口。
- 状态不仅靠颜色表达；表格使用语义表头，交互控件有可读名称、键盘焦点和展开/收起状态。
- 中英文使用一致的分区结构；超长标题、验收内容、步骤和证据文件名允许换行，不以截断隐藏关键事实。

## 空、加载和错误状态

- 项目加载时显示页面骨架和项目标识；加载失败提供重试并保留来源返回操作。
- 每个空分区解释尚无数据的含义，并提供与现有能力相符的入口，例如从 DSH 对话补充、创建质量任务或打开项目文件。
- 无覆盖、未评审、无逐用例执行结果、无证据包是不同状态，文案不可合并成单一“暂无数据”。
- 搜索无结果时显示当前筛选条件和清除入口；单条实体缺少可选字段时隐藏空字段，不渲染占位长横线。
- 保存、评审状态变化、执行取消/重试和证据校验等动作保持当前成功/失败反馈与服务端事实，不在客户端乐观宣告质量结论。

## 约束与实施边界

- 前端继续使用 `public/` 下的原生 HTML、CSS 和浏览器端 JavaScript，不添加生产依赖或构建步骤。
- 优先复用现有项目字段、渲染器、API、SSE 刷新和行动项跳转；合并抽屉与全页中重复的展示逻辑时只改变交互职责，不顺手重写无关页面。
- 现有需求 `links` 能表达需求到用例的覆盖和验证点；用例字段能展示步骤、预期和状态；质量任务、计划、运行、证据包、门禁和报告都已有数据实体。
- 由于当前运行数据没有通用的逐用例结果契约，本轮不得新增或推导逐用例执行结果。后续若需要该能力，另行设计数据契约与证据来源。
- 页面导航可先沿用应用现有视图状态；首页行动项现有目标包含 `overview`、`qualityTasks`、`milestones` 和 `gates`，实施时需映射到新的分区并继续定位具体实体。项目概况复用现有 Action Queue 的事项类型与排序；现有 `GET /api/action-queue` 可增加可选 `projectId` 过滤参数，必须先按项目过滤、再应用 `limit`，避免全局前 50 条造成项目事项缺失。不得从客户端另写一套行动项判定和排序。实施者应保留来源视图和当前分区，并在代码结构中避免另建第二套项目详情数据缓存。
- 当前质量任务默认处于 `intake`，需要风险确认时进入 `confirmation`；没有通用的完成状态。因此验收覆盖任务阶段徽标和待确认项优先顺序，不验收“已完成任务”分组。
- 项目材料当前只保留最近六条；“近期动态”不代表完整审计轨迹。未来日程必须与过去动态分开，并保留知识、纪要等原记录的访问入口。
- 当前测试用例的规范状态是 `draft`、`reviewed`、`executed`；兼容缺失/未知状态和失效链接时主状态优先显示“需核对”，并保留异常计数，不能把它们视为已评审覆盖。

## 验收标准

1. 从项目看板主体进入项目后直接看到完整项目详情；从“快速预览”可清楚进入同一完整详情。
2. 快速预览不包含完整需求/用例/执行/证据工作流，并能关闭回到原项目列表。
3. 项目详情不再用十个同级标签承载所有信息，且视觉上不再像嵌套的浮层卡片；六个分区覆盖现有项目详情实体，主要实体可从概况或相关分区找到。
4. 用户可以从一个需求行看见覆盖数量与验证点，展开后查看关联用例的完整验证步骤，并能识别未覆盖需求和未关联用例。
5. 项目概况、行动项、质量任务、执行、证据和门禁之间的跳转保留上下文；现有行动项目标映射到正确的新分区，同一任务从多个入口打开时显示一致信息。项目概况行动项来自项目范围 Action Queue，保留其排序和错误状态语义。
6. 运行摘要、证据完整性和人工门禁结论能区分；没有逐用例结果时不会展示虚假的用例 PASS/FAIL。
7. 主要浏览与展开操作在窄屏可完成，内容可读、不被半屏容器截断；桌面完整详情占应用主内容区，不是受限尺寸的卡片或抽屉。
8. 中文与英文页面结构一致，加载、错误、空结果和无覆盖状态均有明确反馈。

## 交由实施者决定

- 在现有 CSS 变量和组件中选取最终间距、表格密度、断点和轻量动效。
- 根据现有事件/行动项字段选择最稳定的时间线来源与排序；不引入新事实模型。
- 按实际导航宽度决定项目概况的关键指标布局，以及任务详情采用展开面板还是页面内详情区。
- 若现有字段的命名或某类记录缺少稳定链接，保留可见信息并指出限制，不虚构持久化关系。
