# DSH QA Workbench 0.6.0：Native QA Execution & Action Desk 设计

> 状态：Draft for review
>
> 本文把旧路线中的 Action Desk 作为 Native QA Execution 的用户入口合并进
> `0.6.0`。它不改变质量事实、TestRun、EvidenceBundle 或 Gate 的所有权。

## 1. 决策与目标

`0.6.0` 保持 Native QA Execution 为主版本主题，同时增加 Action Desk 作为
执行状态和质量阻断项的 action-first 首页体验。发布标题建议使用：

```text
Native QA Execution & Action Desk
```

用户打开工作台后应能完成以下闭环：

1. 从已登记且当前启用的 Execution Profile 预览，并由用户确认一次受控 Host Execution。
2. 在执行过程中看到 queued/running、失败、取消、超时和 provider error。
3. 在执行结束后知道 Evidence 是否已完成、是否需要人工处理。
4. 从首页的“需要你处理”队列直接跳到执行、证据、门禁、项目或 DSH 对话。

Action Desk 是质量事实的只读投影，不是第二套质量数据模型，也不负责计算或
修改 Gate verdict。

## 2. 当前基线与问题

当前首页已经有指标卡、日历、在办项目、最近动态和“需要你处理”区域；服务端
通过 `GET /api/board` 返回 `reminders`。现有提醒主要覆盖里程碑、项目流程和
待审批门禁，不能完整表达 Host Execution 的生命周期、Evidence 缺失或失败后
需要采取的动作。

当前 `0.6.0` Native QA Execution 计划已经定义：

```text
Execution Profile
  → HostExecution adapter
  → TestRun provenance
  → EvidenceBundle finalize + verify
```

如果没有统一的行动入口，执行状态会停留在项目详情内，用户仍需要自己寻找
失败运行、未完成证据和阻断门禁。因此，本版将 Action Desk 做成首页现有
attention panel 的规范化升级，而不是新增一个平行顶级页面。

## 3. 范围

### 3.1 本版包含

- 统一的 `ActionItem` 纯函数聚合器，读取现有项目、质量任务、TestRun、
  EvidenceBundle、Gate 和 Host Execution 状态；旧 `reminders` 只通过明确的
  compatibility projection 由它派生。
- `GET /api/action-queue` 只读接口，默认返回最多 50 条、稳定排序的行动项。
- 首页以 Action Queue 作为“需要你处理”区域的唯一数据源；保留指标、日历、
  在办项目和最近动态等辅助区域。
- Host Execution 状态与 Action Queue 的映射：queued/running 可监控，failed、
  cancelled、timed_out、provider error、证据不完整需要处理。`running` 保留在
  队列中但标记 `actionRequired: false`，不冒充待办。
- Gate `BLOCK`/`WARN`、待审批 Gate、确认阶段的关键风险、逾期/临期里程碑和
  既有流程提醒的聚合。
- Action Item 到项目详情允许 Tab 或 DSH 对话的安全跳转；执行详情和 Evidence
  复用现有 `qualityTasks` Tab，不新增顶级路由。
- 质量实体和 Host Execution 更新后的 SSE 刷新。
- 独立模式中的 fake adapter、Action Queue、API 和浏览器 E2E 覆盖；真实 Host
  evidence 与 fake evidence 分开记录。

### 3.2 本版不包含

- AI 失败解释、变更影响分析、回归推荐或 Gate 推荐；这些属于 `0.7.0`。
- 任意 Shell 执行、未登记的 MCP server、生产凭证或任意 Host mount。
- Action Desk 自己写入 TestRun、Evidence、Gate 或替代人工审批。
- 多 Agent 编排、自动发布和 Autonomous QE。
- 将旧 Action Desk 中的 `QA_SKILLS_ROOT` 路径治理强行绑定到执行主链路；如需
  保留，作为独立的低风险维护任务，不阻塞本版核心执行闭环。

## 4. 领域边界与数据流

```text
已登记 Execution Profile
        │
        ▼
HostExecution request / result
        │
        ├── TestRun status + provenance
        ├── staging artifacts
        └── EvidenceBundle finalize + verify
                    │
                    ▼
             trusted quality facts
                    │
                    ▼
          buildActionQueue(snapshot)
                    │
                    ├── GET /api/action-queue
                    └── 首页“需要你处理”
```

Host Execution 仍是执行事实的来源，TestRun 仍是运行事实的来源，EvidenceBundle
仍是证据完整性的来源，Gate 仍是确定性质量判断的来源。Action Queue 只读取这些
事实并生成短生命周期的显示项，不持久化一个新的 `actionItems` 数组。

### 4.1 Execution Profile 与 adapter 边界

现有项目级 `project.executionProfiles` 继续作为唯一 Profile 存储位置；没有
`kind` 的历史 profile 按 `kind: 'local'` 处理，现有 `node-test`/`playwright`
执行路径保持不变。Native Host profile 使用 `kind: 'host'`，其当前版本至少包含
`provider`、`capabilities`、`targetPolicy`、`artifactPolicy` 和 `timeoutMs`；不把
profile 嵌套到 `qualityTasks` 中。

- Browser Use/Computer Use 的 target 必须是 Profile `targetPolicy` 允许的 URL/origin。
- MCP 的 target 必须是已登记 `serverId + toolName`，不能携带任意 command、server URL
  或未登记 server。
- `provider + capability` 由服务端 adapter registry 白名单校验。独立模式没有真实
  adapter 时只能产生 `BLOCKED`/`NOT_RUN` 的受控状态，不能用 fake 成功冒充 Host evidence。
- adapter 只接收 normalized request，并返回受控 status、artifact descriptor、error
  code 和 bounded summary；不能让模型文本直接变成命令或绝对路径。

### 4.2 ActionItem 最小契约

```js
{
  id: 'run_failed:project_1:run_1',
  kind: 'run_failed',
  priority: 'high',
  status: 'needs_action',
  actionRequired: true,
  projectId: 'project_1',
  entityId: 'run_1',
  projectTitle: '支付项目',
  titleKey: 'action.runFailed.title',
  reasonCode: 'provider_error',
  reasonArgs: { provider: 'browser-use' },
  dueAt: null,
  source: { type: 'test-run', id: 'run_1', attemptGroupId: 'group_1' },
  target: { view: 'project-detail', tab: 'qualityTasks', entityId: 'run_1' }
}
```

约束如下：

- `id` 由 `kind + projectId + entityId` 稳定生成，用于去重和 E2E 定位。
- `titleKey`、`reasonCode` 和 `reasonArgs` 是稳定的双语数据契约；API 不直接返回
  面向用户的中文或英文句子。前端通过 i18n 生成显示文本，原始 provider error
  只在受控详情中以转义、限长后的摘要展示。
- `target` 只能由服务端生成的有限组合构成：`view` 为 `project-detail` 或
  `assistant`；`project-detail` 的 `tab` 只能是 `overview`、`qualityTasks`、
  `milestones` 或 `gates`；`assistant` 的 `tab` 必须为 `null`。不能接受客户端
  提交任意 URL 或命令。执行和 Evidence 当前统一跳到 `qualityTasks`，因为现有
  Workbench 没有独立的 execution/evidence 顶级 Tab。
- `status` 只描述用户界面动作状态：`needs_action`、`in_progress`、`blocked`；
  `actionRequired` 明确该项是否需要人工动作。
  源事实变化后，Action Item 消失或变为另一项；不新增 resolved 存储。
- Action Queue 不包含客户端选择的 verdict，也不把 `passed` 显示为可信 PASS；
  只有现有 Evidence finalize/verify 和 Gate contract 才能决定质量结论。

### 4.3 最小行动类型

首批至少支持：

- `run_failed`
- `run_cancelled`
- `run_timed_out`
- `run_running`
- `evidence_incomplete`
- `gate_block`
- `gate_warn`
- `gate_approval`
- `quality_task_confirm`
- `milestone_overdue`
- `milestone_due`
- 现有项目流程提醒

运行类型和 provider 放入 source 或展示元数据中，不为每个 provider 创建一套
Action Item 模型。

`queued` 和 `running` Host/TestRun 都映射为 `run_running`、`status: in_progress`、
`actionRequired: false`；现有 local runner 的 `environment-error` 映射为
`run_failed` + `reasonCode: provider_error`。Host `timed_out` 映射为现有 TestRun 的
`timed-out`，Host `provider_error` 不得被当成 passed。

同一个逻辑 Host Execution 的重试必须携带稳定的 `attemptGroupId`。当新的尝试
进入 queued/running 后，旧尝试的 terminal action item 被标记为 superseded，
首页只显示该 attempt group 的最新需要处理项；历史运行和历史证据仍在项目详情
中保留。没有 `attemptGroupId` 的 legacy local run 按独立 `runId` 去重。

### 4.4 Host → TestRun → Evidence → Gate 闭环

HostExecution 的外部状态固定为 `queued`、`running`、`passed`、`failed`、
`cancelled`、`timed_out`、`provider_error`、`blocked` 和 `not_run`。它不是第二套
质量运行模型，而是受控 Host 执行的审计记录；对应的 TestRun 使用现有 `mode: 'local'`
形状，增加 `resultTrust: 'controlled-host'` 和 `provenance.hostExecutionId`。

状态映射固定如下：

| HostExecution | TestRun | Gate 语义 |
| --- | --- | --- |
| `passed` | `passed` + 完整 Host provenance | 只有 Evidence finalize/verify 成功后才可能通过 |
| `failed` | `failed` | BLOCK |
| `cancelled` | `cancelled` | BLOCK |
| `timed_out` | `timed-out` | BLOCK |
| `provider_error` | `environment-error` + `errorCode: 'provider_error'` | BLOCK |
| `blocked` / `not_run` | `environment-error` + `errorCode: 'provider_unavailable'` | BLOCK |

`passed` 的 Host summary 没有 terminal provenance、受控 artifact 或 verified
EvidenceBundle 时不得产生 PASS；Host `resultTrust: 'controlled-host'` 必须与现有
`controlled-local` 一样进入 Gate 的受控运行校验，并额外要求对应 EvidenceBundle
`state: 'ready'`、`integrity: 'verified'`。Gate 只读 TestRun/Evidence facts，不读取
Action Queue，也不接受客户端 verdict。Host artifact descriptor 必须先物化到现有
TestRun staging 目录，再调用既有 `finalizeEvidence()`，不得直接写 ready bundle。

## 5. API、事件和首页交互

### 5.1 Action Queue API

```text
GET /api/action-queue?limit=50
→ {
    ok: true,
    items: ActionItem[],
    generatedAt: string
  }
```

接口只读；支持可选查询参数 `limit`，必须是 1–50 的整数，缺省为 50。排序键
固定为 `priorityRank(desc) → actionRequired(desc) → statusRank(desc) →
dueAt(asc, null-last) → projectId(asc) → entityId(asc)`，保证同一输入的返回顺序
稳定。优先级至少固定为 `critical`：`gate_block`、`evidence_incomplete`；`high`：
`run_failed`、`run_cancelled`、`run_timed_out`、`milestone_overdue`；`medium`：
`gate_approval`、`gate_warn`、`quality_task_confirm`、`milestone_due`；`low`：
`run_running` 和既有流程提醒。状态排序固定为 `blocked > needs_action >
in_progress`。无项目或无行动项返回结构化空状态；数据源暂不可用返回 `503` 和
明确错误，不用空队列掩盖服务故障。

错误响应使用 `{ ok: false, code: 'ACTION_QUEUE_SOURCE_UNAVAILABLE', error }`；`limit`
非法使用 `400`，数据源不可用使用 `503`。

现有 `GET /api/board` 和 `reminders` 保留兼容形状。`toLegacyReminders(items)`
是唯一兼容转换层：保留旧字段 `type/title/date/severity/days/projectId/
projectTitle`，其中 `milestone_* → milestone`、`gate_* → gate`、其他行动项
映射为 `workflow`；里程碑和 Gate 沿用已有的安全标题，执行类行动项使用受控的
legacy 文案字典，不能直接复制 provider 原始错误；`date` 取 `dueAt` 的日期部分，
`days` 由 `dueAt` 相对 `now` 计算，无截止时间时保持旧的空字符串形状；`severity`
至少按 `critical/high → danger`、`medium → warning`、`low → normal` 映射，
`gate_approval` 保留 `review`。新首页不再依赖这些旧字段。旧转换只保留兼容展示，
不参与新的排序、状态判断或质量结论。

### 5.2 SSE 刷新

以下事件需要触发 Action Queue 重新拉取，并按 300ms 防抖合并刷新：

- `quality.task.updated`
- `quality.test-run.updated`
- `quality.evidence.updated`
- `quality.gate.updated`
- `quality.host-execution.updated`

本版固定持久化规范化 HostExecution 记录，保存于项目的 `hostExecutions` 集合，至少包含 `id`、`projectId`、
`qualityTaskId`、`attemptGroupId`、`provider`、`status`、`profileVersion`、
`testRunId`、`revision`、`updatedAt`、受控 `errorCode` 和可选 `supersededBy`。历史
项目通过 schema migration 得到空的 `hostExecutions` 数组。每次状态变化发送：

```js
quality.host-execution.updated = {
  projectId, entityId, attemptGroupId, status, revision, updatedAt
}
```

Host 结果映射到 TestRun 后，仍发送现有 `quality.test-run.updated`；两类事件的
职责不能互换。SSE 重连或收到 `hello` 后必须重新拉取 Action Queue。

### 5.3 首页

- 继续使用当前 `#dashboard-reminders` 区域，不新增 Action Desk 顶级导航项。
- 将其升级为 canonical Action Queue 渲染器，展示 priority、status、reason、
  project 和 CTA；`actionRequired: false` 的 running 项使用监控样式或折叠到
  “运行中”区。
- 指标卡、日历、在办项目和最近动态保留，但视觉优先级低于需要处理队列。
- queued/running 只显示可监控状态；失败、超时、证据不完整和 Gate BLOCK 显示
  明确动作按钮。
- 空状态说明“当前没有需要处理的事项”，不能用 `PASS` 或绿色成功语义代替。
- 中英文 key 必须成对提供；独立模式显示能力不可用时的 `NOT_RUN` 或 `BLOCKED`
  边界。

## 6. 实施顺序

1. **HostExecution contract**：在不破坏 local profile 的前提下冻结 host profile、
   adapter registry、状态映射和 artifact descriptor。
2. **HostExecution persistence/events**：固定 `hostExecutions` 记录和
   `quality.host-execution.updated` 契约，与 TestRun 事件分别测试。
3. **Host evidence integration**：完成当前 0.6 adapter、TestRun provenance、
   Evidence finalize/verify，并覆盖 retry/superseded 规则。
4. **Action Queue contract/API**：创建纯函数和 ActionItem fixture，增加
   `GET /api/action-queue`，验证空状态、排序、limit、非法参数、数据源错误和不写 Store。
5. **Homepage integration**：将“需要你处理”接到 canonical queue，增加 CTA、
   status、双语渲染和 SSE 重连后的重新拉取。
6. **End-to-end verification**：fake adapter 证明执行到 Evidence 的闭环；浏览器
   E2E 证明首页刷新、跳转、重试去重和双语；真实 Host smoke 单独记录 provider
   evidence。

## 7. 验收标准

- `ActionItem` 聚合器对同一输入稳定、无副作用、可单测。
- API 返回结构固定，`limit` 只允许 1–50，排序有稳定 tie-breaker，重复调用不
  产生 Store 写入；数据源错误不能伪装为空队列。
- Host Execution 的失败、取消、超时、断线、重试和 Evidence 不完整都能在首页
  产生正确的行动状态；新的 retry 会隐藏旧 attempt 的重复行动项。
- `Gate BLOCK/WARN`、待审批 Gate、逾期/临期里程碑和既有流程提醒不回退。
- 首页无需整页刷新即可在相关 SSE 后更新队列。
- 每个行动项能跳到允许的项目详情 Tab 或 DSH 对话上下文；不存在的项目/Tab
  有可验证的降级错误状态。
- 中文和英文界面均不直接展示另一语言的 title/reason；reason code、args 和
  provider error 摘要都有 schema 与长度边界。
- provider error、imported-summary、未 finalize artifact 或缺少 provenance 均不
  能产生 `PASS`。
- 通过 `npm run test:unit`、`npm run test:e2e`、`npm test` 和 `git diff --check`；
  fake adapter 与真实 Host smoke 的证据分别记录。

## 8. 风险与取舍

| 风险 | 缓解 |
| --- | --- |
| 0.6 变成两个大版本拼接 | Action Desk 只做只读投影和首页入口，执行与证据仍是主线 |
| 首页出现两套提醒 | 以 `buildActionQueue` 为唯一聚合边界，旧 reminders 只做兼容投影 |
| Action Queue 被误解为质量结论 | UI 显示 action/status/reason，不显示伪造的 PASS；Gate 继续独立计算 |
| Host provider 状态无法刷新 | 统一 SSE 事件并覆盖事件重连后的重新拉取 |
| 旧 Action Desk 范围继续膨胀 | Skills roots、AI 建议、变更分析和回归推荐留在独立版本/任务 |
